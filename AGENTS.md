# AGENTS.md — cockpit

**cockpit** is a provisional working name. It appears in the desktop app (`Cockpit`, `com.cockpit.desktop`).

## Rule #1: no over-engineering

Do not add any abstraction, package or app beyond what this file describes. When in doubt, do the simplest thing.

## Technical choices: long-term viability first

When choosing a tool, library or framework, the criterion is long-term viability: who maintains it (an organization or a single person), release activity, real adoption, compatibility with the rest of the stack, and the cost of leaving it. Setup speed and amount of configuration are not arguments. Back the choice with verified facts.

## Language

Everything in this repository is written in English: code, identifiers, comments, documentation, branch names, commit messages, and pull request titles and descriptions.

## Product

A desktop application that drives agent CLIs (Claude Code, Codex, OpenCode, Kimi, Mistral, Cursor CLI…) through node-pty, following Superset's projects / workspaces model.

Differentiators:
- sessions outside any project (multi-agent exploration without a repository);
- artifacts on storage you own;
- usage statistics.

The repository is built in steps. So far, the parts in scope are the **desktop app shell** (`apps/desktop`): a window, a router, a typed bridge to the main process, and the UI foundation (styling, light and dark themes, sidebar layout); and the **pty host** (`packages/pty`), which runs node-pty in a utility process and exposes it as `window.api.pty`; the **login-shell environment** (`packages/shell-env`), which the main process resolves at startup for the child processes it will spawn; the **state store** (`packages/state`), which keeps the app state in a JSON file; the **workspaces package** (`packages/workspaces`), which creates, lists and removes git worktrees (`listBranches` feeds the base choice); and the **harnesses package** (`packages/harnesses`), which catalogues the agent CLIs and detects which are installed. The product UI is the **terminal page** (`/terminal`): xterm.js connected to shells through `window.api.pty`, in tabs and splits that keep running when the user goes to another page, and the **projects** section of the sidebar: add, list and remove git repositories through `window.api.projects`, and create, list and delete their workspaces (git worktrees) through `window.api.workspaces`; and the **sessions** section of the sidebar: start an agent CLI in a folder of its own, outside any project, or in a workspace's worktree, through `window.api.sessions`.

Daemon, artifacts, stats, cloud backend, web app, mobile: create none of these without an explicit request.

## Monorepo

- **No business logic in `apps/`.** Everything lives in `packages/`; apps only wire things together.
- **Bun** (package manager, workspaces, script runner) + **Turborepo**, TypeScript.
- Runtime: **Node 22+** for the tooling, the oldest supported LTS line; the desktop app runs on the Node bundled with Electron (24 in Electron 44). A native module (`node-pty`) must be built for the runtime that loads it.
- Set up by hand, without the `create-turbo` template:
  - root `package.json`: `apps/*`, `packages/*` and `.github/scripts/plane-sync` workspaces, scripts that delegate to Turbo;
  - `turbo.json`: `build`, `dev`, `test`, `typecheck`, `lint` tasks. `test` is never cached: its result depends on the machine (the Electron binary, the user's login shell), not only on the files, and Turbo shares its local cache across git worktrees. `lint` is never cached either (`"cache": false`), so a change to `.oxlintrc.json` is never hidden by a cached result;
  - `tsconfig.base.json`, extended by every package;
  - `.oxlintrc.json`: the one oxlint config, shared by every workspace (no per-package config).
- Internal dependencies declared as `"workspace:*"`.
- **Linting: oxlint.** Every workspace has a check-only `"lint": "oxlint"` script, without `--fix` (no fix script), and `bun run lint` runs them all through Turbo, uncached. The root `.oxlintrc.json` enables oxlint's default plugins plus `react`, the `correctness` category as `error`, and ignores the generated `routeTree.gen.ts`; oxlint also skips git-ignored paths. Type-aware rules, other categories and formatting are not set up. `oxlint` is a root `devDependency`, like `typescript`.
  - Why oxlint (facts checked on 2026-10-21 against npm, the GitHub API and the official sites): it is built by VoidZero (Evan You's company: Vite, Vitest, Rolldown), which Cloudflare acquired on 2026-06-04 with the projects staying MIT; releases are weekly (1.0.0 on 2025-06-10, 1.89.0 on 2026-10-19); about 16.2 million downloads a week and 23,159 stars on `oxc-project/oxc`; it has its own Rust parser and is the only one of the three aligned with TypeScript 7, which the repo uses. Its npm publisher is a single account (`boshen`), while the code lives in an organization owned by a company.
  - Against Biome (`biomejs` org, community-run, about $30k a year from sponsorship, 11.0 million downloads a week, 25,979 stars, own rule names and config format, so a medium exit cost) and ESLint with typescript-eslint (ESLint: OpenJS Foundation, 96.1 million downloads a week, 27,569 stars; typescript-eslint: 55.6 million downloads a week, 16,435 stars): typescript-eslint 8.72.0 declares `typescript >=4.8.4 <6.1.0` and imports TypeScript's JS API, which TypeScript 7 does not ship, so linting this repo would need TypeScript 6 installed side by side until TS 7.1 support lands.
  - Exit cost: low. oxlint's rules are ports of ESLint, typescript-eslint, unicorn and react rules under the same names, and its config is shaped like ESLint's.
  - oxlint ships weekly and `^1` lets a new correctness rule fail CI after a lockfile update; the lockfile pins the version CI uses, so that only happens with a deliberate `bun update`.

- **Internal packages consumed as TS source**, with no separate per-package build.
- **Tests** with `vitest`.

## Desktop app (`apps/desktop`)

- **Stack**: Electron 44, electron-vite (dev server and build), electron-builder (packaging), React 19, TanStack Router with file-based routes.
  - electron-builder rather than Electron Forge: Forge does not support Bun, and its Vite plugin leaves `node_modules` out of the package, which breaks native modules such as node-pty.
  - electron-vite has a single maintainer. It is a thin layer over Vite: if it is abandoned, replace it with Vite and a dev script. Packaging does not depend on it.
- **UI**: Tailwind CSS 4, shadcn/ui components on Base UI (`base-mira` style, made for dense interfaces), lucide icons, the system font.
  - Tailwind is a build-time tool maintained by Tailwind Labs. Its team shrank in January 2026 but releases continue; a frozen version keeps working.
  - shadcn/ui is not a runtime dependency: its CLI copies component source into the repo, which we own and edit. Base UI is maintained by the MUI company and is shadcn's default since July 2026.
  - Components import `cn`, shadcn's class merger, still young (0.x since September 2026). If it is abandoned, replace it with `clsx` + `tailwind-merge`, which have the same API.

```
src/
  main/       # main process: window, `app://` protocol, IPC handlers
  preload/    # exposes `window.api`, nothing else
  shared/     # the `Api` contract, types only
  renderer/   # React app
    routes/         # file-based routes; `__root.tsx` holds the sidebar layout
    components/     # app components
      ui/           # shadcn/ui components, added by the CLI
    styles.css      # Tailwind entry and theme tokens
```

- **Renderer boundary.** The renderer never imports `electron` or Node modules. It reaches the main process only through `window.api`, typed by `Api` in `src/shared/api.ts`. A future web app (TanStack Start) implements the same `Api` over HTTP and reuses the routes.
- **No web app or shared UI package** until a web target exists. When it does, move the renderer into a package consumed by both apps.
- **Security**:
  - `contextIsolation` and `sandbox` on, `nodeIntegration` off. A sandboxed preload cannot be an ES module, so it is bundled as CommonJS (`index.cjs`).
  - The built renderer is served from the `app://renderer` protocol, never `file://`, with a CSP in `index.html`. The router therefore uses real URLs, as on the web.
  - New windows are denied (`https` links open in the system browser), and navigation away from the app origin is blocked. The guard compares origins rebuilt from protocol and host (`URL.origin` is `"null"` for `app:`, so it would let `app://other/` through). `about:blank` is not covered: Chromium commits it synchronously, with no `will-navigate`, and only the app's own code can navigate there. `navigateOnDragDrop` is off: a dropped file does not navigate the window, and drops do nothing until a feature handles them.
  - Every privileged IPC handler in the main process (`pty:*`, `projects:*`, `workspaces:*`, `sessions:*`, `get-shell-path`) ignores a message whose sender frame is not the app's own page (`app://renderer`, or the dev server origin in dev); an invoke handler rejects.
- **Dependencies**: everything the bundles import goes in `devDependencies`, and electron-vite bundles it. Only modules that cannot be bundled (native modules such as node-pty) go in `dependencies`, so electron-builder ships them and rebuilds them for Electron.
- **Styling**:
  - Tailwind utilities with the semantic tokens defined in `styles.css` (`bg-background`, `text-muted-foreground`, `bg-sidebar`…), never raw colors or `dark:` color overrides.
  - Use a shadcn/ui component before writing custom markup. Add one with `bunx --bun shadcn add <name>` from `apps/desktop` (`components.json` lives there, and `tsconfig.json` carries the `@/` alias only for the CLI). The CLI adds packages to `dependencies`: move them to `devDependencies`.
  - Add a component when a feature uses it, not ahead of time.
- **Theme**: follows the system through `prefers-color-scheme`, which Electron drives from `nativeTheme`. Dark tokens live under `@media (prefers-color-scheme: dark)`, not a `.dark` class; if the shadcn CLI adds a `.dark` block, move its variables there. A theme setting, when requested, sets `nativeTheme.themeSource` in the main process, which switches the page and the native window chrome together.
- **Window chrome**: on macOS the title bar is hidden and the window controls sit in the sidebar's top strip. The top strips of the sidebar and of each page header drag the window (`app-drag`); an interactive element inside one needs `app-no-drag`. Other platforms keep the native frame.
- **Generated route tree**: `src/renderer/routeTree.gen.ts` is generated by the router plugin on `dev` and `build`, and committed so `typecheck` works on a fresh checkout.
- **Output**: electron-vite builds to `dist/` (the Turbo `build` output), electron-builder packages to `release/`.
- **Packaging**: `package` builds an ad-hoc signed `Cockpit.app` for the current platform. Developer ID signing, notarization, installers and auto-update come later, on request.
- **Electron binary**: since Electron 42 the `electron` package no longer downloads its binary on install; it does so the first time `require('electron')` runs. electron-vite reads the binary path without triggering that download, so `dev` runs `install-electron` first (a no-op once the binary is there).
- **Login-shell environment**: an app started from the Finder or the Dock gets launchd's minimal `PATH`, so the main process resolves the environment of the user's login shell once per launch (`resolveShellEnv` from `@cockpit/shell-env`, exported as `shellEnv` by `src/main/shell-env.ts`). Anything that spawns a child process (git, harness detection) must spawn with `await shellEnv`. A pty's `env` defaults to it (see Spawn defaults), and the shell it runs is the one that environment's `SHELL` names. The renderer only gets `PATH`, through `window.api.getShellPath()`.
- **Terminals**: node-pty runs in an Electron `utilityProcess`, not a daemon, so a pty crash does not take the app down. Sessions therefore end when the app quits. Any update flow must warn the user, before restarting, that the running sessions will be terminated.
  - `packages/pty` holds the logic and does not import `electron`: `runPtyHost(port)` runs in the utility process and owns the node-pty sessions, `createPtyClient(fork)` runs in the main process (numbered sessions, spawn request and ack, data and exit fan-out, and the host's restart). `apps/desktop` only wires them: `src/main/pty-host.ts` is the utility process entry (forked through electron-vite's `?modulePath` import), `src/main/index.ts` forwards the `pty:*` IPC and sends data and exit events to the window that spawned the session, and the preload exposes `window.api.pty`.
  - **The host restarts lazily.** The client takes a function that forks the utility process (`() => utilityProcess.fork(…)`), calls it at creation, and again in the first `spawn` after the host exited; spawns issued together share the new host. If the utility process dies, its open sessions end with `exitCode: null` and a `spawn` still waiting for it rejects with `pty host is not running`. Session ids keep counting across hosts, so an id of a dead host is never reused: `write`, `resize` and `kill` on it do nothing to a new session, and whatever an old host still sends is ignored. No crash-loop handling: a host that dies at once is forked again by the next spawn.
  - **Terminal page** (`src/renderer/components/terminal-tabs.tsx`, route `/terminal`): tabs and splits that survive leaving the page (the tab state is module-level, so a visit finds the tabs, splits, selection, output and running shells as they were; only a reload, a window close or a quit ends them). The tab bar (shadcn `tabs`, "Terminal N" with a sibling "Close Terminal N" button, and a "New terminal" button) sits in the page header, passed as `children` of `PageHeader`. Tab numbers count up for the page's lifetime and are never reused; closing the selected tab selects the one on its left, and with no tab left the page shows "No terminal open" and a "New terminal" button. A tab's terminals form a binary tree of equal halves ("Split right" or "Split down", nestable, no drag resize); each terminal has "Split right", "Split down" and "Close terminal" buttons shown on hover and focus. **Flat layout**: every terminal of every tab is rendered in one list keyed by a terminal id and absolutely positioned from its tab's tree (percent boxes), so a split, a close or a tab switch never remounts a view; the terminals of other tabs are `invisible` and keep their size. A pane's terminal is a live terminal (`live-terminals.ts`, see Sessions), created and spawned (at 80 x 24, resized once `spawn` resolves if its size changed) when the pane first renders; the module-level `dispatch` closes the terminals an action removes ("Close Terminal N", "Close terminal"), which kills their shells, so closing ends a shell and leaving the page does not. The terminal component (`terminal.tsx`) is only the view: it moves the live terminal's element into its container and out again, skips `fit()` while its area has no size, and takes the keyboard when its `focused` prop turns true (a new terminal, a re-selected tab, the sibling of a closed one: in `A | (B / C)`, closing C focuses B, not A). Colors come from the page tokens (the 16 `--terminal-*` ANSI tokens, light and dark; background, foreground, cursor and selection reuse existing tokens) and are read again when the color scheme changes. Copy and paste use Electron's default macOS Edit menu, which fires the DOM events xterm.js handles.
  - **Early keys**: keys typed before `spawn` resolves are held and written to the shell, in order and in one write, right after the session id is set. They are discarded if the spawn rejects (a `failed` flag stops holding them), the shell has already exited or the terminal is closed first. A rejected spawn writes `[Could not start the shell: …]` in the terminal, unless its pane was closed meanwhile. The tty buffers them until the shell reads, so its own startup loses nothing.
  - **Spawn defaults**: `window.api.pty.spawn` only needs `cols` and `rows`. The main process fills in the rest (`withSpawnDefaults` in `src/main/index.ts`): the `SHELL` of `await shellEnv` (`/bin/zsh` when unset) as a login shell (`-l`), the home directory, and `await shellEnv` as the environment with `TERM=xterm-256color` and `COLORTERM=truecolor`. Options the renderer passes win. `-l` belongs to the default shell only: a request with its own `command` and no `args` runs it with no argument.
  - **Sessions end with their page**: the main process kills a window's sessions when its main frame commits another document (`did-navigate`, a reload included) or the window is destroyed, or, for a navigation that ends on an error page (a URL such as `/%`, which Electron refuses with `did-fail-load` code -9; a 404 from the `app` protocol does commit a document and is killed through `did-navigate`), `did-fail-load` on the main frame with any code but `ERR_ABORTED` (-3), so a navigation the guard blocks kills nothing. Route changes are same-document and kill nothing; a terminal closed in the page kills its own shell. **Late spawn ack**: each page has a count of the times its shells were ended, and `spawnFor` reads it before the spawn; a spawn that resolves after its page navigated or was destroyed (the pty host was stopped or busy) kills the pty at once and throws `PageGoneError`: `sessions:start` lets it reach its existing `catch`, which removes the folder and saves nothing, while the `pty:spawn` handler catches it and returns `-1` (the reply reaches no page), so Electron logs no `Error occurred in handler`, which the tests count as an error, and a reloaded page leaves no orphan shell.
  - **Quit**: no shell survives `app.quit()` (Cmd+Q). Nothing kills them explicitly on `will-quit`: the windows are destroyed, which kills their sessions, and the pty utility process is terminated with the app. A packaged-app test checks it with two shells.
  - **Transport: IPC, not a `MessagePort`.** Each output chunk goes host, then main (`parentPort`), then renderer (`webContents.send`). Electron can transfer a `MessagePortMain` to a utility process and to a renderer, and the `window.api.pty` contract is the same either way, so moving later stays inside `packages/pty`, `main` and `preload`. No measurement shows IPC as a bottleneck for one terminal. **Trigger to move**: a measurement showing typing latency, or a saturated main process, with several terminals active at once (agent sessions).
  - **xterm.js** (`@xterm/xterm` `^6.0.0`, `@xterm/addon-fit` `^0.11.0`, stable releases rather than the 6.1 beta line VS Code tracks): repository `xtermjs/xterm.js` (organization), MIT, 21,285 stars, last push 2026-10-13; npm maintainer tyriar (Daniel Imms, VS Code terminal); VS Code depends on `@xterm/xterm` and its addons. About 3.9 million downloads a week for `@xterm/xterm` and 3.4 million for `@xterm/addon-fit` (week of 2026-10-12). Stable releases are rare (5.4.0 2024-03-01, 5.5.0 2024-04-05, 6.0.0 2025-12-22) but the 6.1.0 beta line is published continuously. Figures checked against npm and the GitHub API on 2026-10-20. Exit cost: contained in one component.
  - **node-pty** is maintained by Microsoft (`microsoft/node-pty`, the terminal backend of VS Code; npm maintainers tyriar, alexr00 and microsoft1es). Adoption: about 2.5 million downloads a week on npm (week of 2026-10-12) and 2,050 GitHub stars. The last push was on 2026-10-15. Release activity in 2026: nine 1.2.0 betas in January, then about one every one to two months, the last (`1.2.0-beta.15`) on 2026-08-03; the latest stable, 1.1.0, is older. Figures checked against npm and the GitHub API on 2026-10-19.
  - **Pin**: exactly `1.2.0-beta.15`, with no `^`. 1.1.0 ships a macOS `spawn-helper` without the execute bit, so every spawn fails with `posix_spawnp failed`; the 1.2.0 line fixes it, and VS Code builds on it, so it is the de facto stable one. Move to 1.2.0 once it is published. The pin appears in `apps/desktop` (shipped by electron-builder) and in `packages/pty` (Bun's isolated linker resolves each workspace's own dependencies).
  - **No rebuild**: `npmRebuild: false` in `electron-builder.yml`. node-pty is N-API, so its macOS prebuilds load under Electron as they are, with no Xcode needed. A rebuild compiled node-pty in place in the shared Bun store (`node_modules/.bun/`), where its `build/` directory then took precedence over the prebuilds for every later run, in dev as well. If a rebuilt `build/` shows up there, delete it.
  - `asarUnpack: node_modules/node-pty/**` keeps `pty.node` and `spawn-helper` outside the asar, where they can run.
  - `spawn` rejects a message from another origin (the sender-frame rule above). The host guards each per-session node-pty call, so a bad size or a call racing a session's exit cannot kill it.
- **State**: the app state lives in one JSON file, `state.json`, in `app.getPath('userData')` (so `COCKPIT_USER_DATA_DIR` isolates it in tests). `version`, `projects` (`{ path }[]`, the repository roots as git reports them, in insertion order) and `sessions` (see Sessions) exist so far; a feature that stores a field adds it, with a write API.
  - `packages/state` holds the logic and does not import `electron`: `loadState(dir)` reads `<dir>/state.json`, creates the folder and writes `{ "version": 1 }` when the file is missing, and `NewerStateError` is what it throws for a newer file. `projects` is optional on disk and reads as `[]` when absent, without rewriting the file (a file from an earlier build stays as it is, version 1). The write API is `saveState(dir, state)` plus the pure `addProject(state, path)` (throws `ProjectExistsError` for a path already listed) and `removeProject(state, path)` (an unknown path changes nothing); they return a new state. The main process keeps the loaded state in memory and replaces it after each successful `saveState`. The main process calls it first thing in `whenReady`, before the pty host and the window, with `userData`.
  - **Atomic, durable write**: every write goes to `state.json.tmp`, is flushed with `fsync`, renamed over `state.json`, then the data folder is opened and `fsync`ed so the rename itself survives a power loss, with synchronous `node:fs` (tiny file). A crash leaves the previous `state.json` intact; a leftover `.tmp` is ignored and overwritten. Node's `fsyncSync` goes through libuv, which on macOS already issues `F_FULLFSYNC` (falling back to `F_BARRIERFSYNC`, then `fsync`), so only the folder sync was missing.
  - **Corrupted file** (not JSON, not an object whose `version` is a positive integer, a `projects` that is not an array of objects with a string `path`, or a `sessions` that is not an array of objects with string `id`, `name`, `harness`, `directory` and `createdAt`, and a `project` that is a string when present): kept as `state.json.corrupt-<timestamp>` with its original bytes (a hard link, so `state.json` is never missing; a copy when the volume cannot link; a name already taken goes to the first free `-2`, `-3`…, and an existing backup is never overwritten), a fresh `state.json` is written, and a warning names the backup.
  - **Newer version** (`version` above the one the app reads): the file is left untouched, no window opens, the message "written by a newer version of Cockpit" goes to stderr (and to an error dialog outside background mode), and the app exits with code 1.
  - **Unreadable file** (a read fails for a reason other than the content: a folder named `state.json` gives `EISDIR`, a file without read permission gives `EACCES`): `loadState` throws the original error and touches nothing. The main process quits as for a newer version (nothing set aside, no window, stderr, error dialog outside background mode, exit code 1) with a message that starts "Cockpit cannot read its data", then names the path of `state.json` and the error message.
  - **Git is the source of truth for worktrees**: the state never stores what `git worktree list` can tell.
  - **Why JSON files rather than SQLite** (facts checked on 2026-10-20): the state is a handful of small records written by one process, and a JSON file has nothing to maintain or leave; leaving it later costs one migration driven by `version`.
    - `node:sqlite` in Node 24.22.0 (bundled by Electron 44.9.0 and 44.9.1): "Stability: 1.2 - Release candidate" since v24.15.0, unflagged since v22.13.0, no `ExperimentalWarning` on load (SQLite 3.53.4). Built in, no native build, but not Stable: its API can still change, and it moves with the Node that Electron bundles.
    - `better-sqlite3` 13.0.3 (2026-08-05): a single npm maintainer (joshuawise), about 1,184 commits from him against 88 for the next contributor, 7.2 million downloads a week (2026-10-12 to 18), 7,522 GitHub stars, last push 2026-08-10. N-API with prebuilds shipped in the package since 13.0.0 (2026-07-21), but still a native module: the `asarUnpack` and shared Bun store concerns already met with node-pty.
- **Projects**: `window.api.projects` has `list()`, `add()` and `remove(path)`. The business rules live in `packages/state` (the list) and `packages/workspaces` (`findRepositoryRoot`); `startProjects` in `src/main/index.ts` only wires them. The three `projects:*` handlers are behind `isFromApp` and an invoke rejects from another origin.
  - **Add**: `add()` opens `dialog.showOpenDialog` (`openDirectory`) on the sender's window, resolves the picked folder to its repository root with `findRepositoryRoot(folder, { env: await shellEnv })`, then `addProject` and `saveState`. It returns `{ status: 'added', project }`, `{ status: 'cancelled' }` or `{ status: 'refused', message }`. A project stores its root path only; `name` is the root's basename, computed on the way out.
  - **Refusals** show as an inline message under the Projects header, replaced by the next refusal and cleared by the next successful add; a cancellation changes nothing. Messages: `<name> is already in Cockpit.`, `<folder> is not in a git repository.` (`NOT_A_REPOSITORY`), and the `WorkspaceError` message for the others (`git is not installed`, `GIT_TOO_OLD`, `GIT_FAILED`).
  - **Remove**: the "…" menu of an entry (shown on hover and focus) holds "Remove from Cockpit" with the muted line "Files stay on disk". No confirmation, nothing deleted on disk, no write when the path is unknown.
  - The root route loader returns `{ version, projects, sessions }`; the sidebar component calls `router.invalidate()` after a change, and the root layout does too when the window gains focus (worktrees added in a terminal show up; the sessions list is read again too). shadcn `button` and `dropdown-menu` were added; the CLI imports `cn` from the `cn` package, and `@base-ui/react`, `class-variance-authority` and `cn` sit in `devDependencies`.
  - **Save failure**: when `saveState` throws while adding, `add()` returns `{ status: 'refused', message: 'Cockpit could not save its data: <error message>' }`, the state in memory is not replaced and nothing is logged.
- **Workspaces**: a workspace is a linked git worktree of a project (the main working tree is the project and is never listed). Git is the source of truth: nothing about workspaces is stored in `state.json`. `projects:list` returns each project with its `workspaces` (`{ path, name, branch }`, in `git worktree list` order, `name` being the branch or the folder name when detached) and, when git cannot list them, an `error` (`<path> is not a git repository.` for `NOT_A_REPOSITORY`, the `WorkspaceError` message otherwise) shown as a muted line under the project, with no workspace.
  - **Where worktrees live**: `$COCKPIT_HOME/worktrees`, with `COCKPIT_HOME` defaulting to `~/.cockpit` (`worktreesRoot` in `src/main/index.ts`), laid out as the package does (`<repo basename>-<8 hex>/<branch>`). Worktrees are the user's code, not app data, so the `userData` rule does not apply, for two reasons: the space in `Application Support` breaks some tools run inside a worktree, and uninstallers such as AppCleaner delete `~/Library/Application Support/Cockpit`, which would wipe uncommitted work.
  - **IPC**: `window.api.workspaces` has `branches(project)`, `create(project, name, base)` and `remove(project, path, { force? })`, behind the `workspaces:*` handlers (`startProjects` in `src/main/index.ts` wires `listBranches`, `createWorktree` and `removeWorktree` with `await shellEnv`). Each is behind `isFromApp` and refuses a project path that is not in the state (`<path> is not a project in Cockpit.`). `create` returns `created` or `refused` (`A branch named <name> already exists.` for `BRANCH_EXISTS`, `<name> is not a valid branch name.` for `INVALID_BRANCH_NAME`, the `WorkspaceError` message otherwise); `remove` always passes `deleteBranch` and returns `removed` with `branchKept` (`BRANCH_NOT_MERGED`), `dirty` (`DIRTY_WORKTREE`) or `refused`.
  - **New workspace**: the project's "…" menu holds "New workspace…" above "Remove from Cockpit". Its dialog, "New workspace in <project>", has a "Name" field (focused, used trimmed) and a "Base" select that lists the local branches under "Local" and the `origin/*` branches under "Remote", with the default base preselected (none when the package finds none, and "Create" stays disabled until one is chosen). No `git fetch`. A refusal shows in the dialog, which stays open; so does a failure to list the branches, with "Create" disabled.
  - **Delete workspace**: the workspace's "…" menu holds "Delete workspace…", which opens a confirmation naming the folder. A branch is deleted only if merged, otherwise the sidebar shows `Branch <branch> was kept: it is not merged.` in the same message slot as the project refusals. Uncommitted changes turn the dialog into a warning ("<name> has uncommitted changes", "Delete anyway"), a second step triggered by `DIRTY_WORKTREE` so there is no race between the check and the removal; "Delete anyway" calls `remove` with `force`. Any other failure shows in the dialog, which stays open.
  - **Layout**: the Projects section takes the height left in the sidebar and its list (`ul`) is the scroll container, so the header and the footer stay in the window. The Sessions section below it takes its content's height up to 40% of the sidebar, its list scrolling past that. shadcn `dialog`, `alert-dialog`, `input`, `label` and `select` were added.
- **Sessions**: `window.api.sessions` has `harnesses()`, `list()` and `start(harness, { cols, rows }, { workspace?, prompt? })`. The rules live in `packages/state` (`Session`, `addSession`, `sessionName`) and `packages/harnesses` (the catalogue and `detectHarnesses`); `startSessions` in `src/main/index.ts` only wires them. The three `sessions:*` handlers are behind `isFromApp` and an invoke rejects from another origin.
  - **Session folders**: `$COCKPIT_HOME/sessions/<id>`, with the same `cockpitHome` as worktrees (`resolve(process.env.COCKPIT_HOME || join(homedir(), '.cockpit'))` in `src/main/index.ts`, see Workspaces). The session folders are the user's work, not app data, so they are not under `userData`.
  - **State**: `sessions` is `{ id, name, harness, directory, createdAt, project? }[]` in creation order (optional on disk, read as `[]` without rewriting the file). `id` is `crypto.randomUUID()`, `harness` the catalogue id, `directory` `<home>/sessions/<id>` (or the workspace's worktree path), `createdAt` ISO 8601, `project` the repository root of the workspace it runs in (absent outside any project, which is how earlier files read; a `project` that is not a string makes the file corrupted). `sessionName(state, harness, directory?)` is `<harness name> <n>`, `n` counting that harness's sessions in `directory`, or those without `project` when it is omitted, so each workspace and the Sessions section number apart (no rename, no removal yet). `sessions:list` returns them newest first. The main process keeps one module-level `state`, shared by projects and sessions, and replaces it after each successful `saveState`.
  - **Detection**: `detectHarnesses(await shellEnv)` runs once per launch, on the first `sessions:harnesses` or `sessions:start` call, never at startup (nothing lists the harnesses until a Start session menu or the New workspace dialog's Agent select opens), so an app that never starts a session, and every test launch that does not, runs no CLI's `--version`. Later calls reuse the result. A CLI installed after launch shows up after a restart.
  - **Start**: `sessions:start` refuses a harness that was not detected (`<name> is not installed.`), creates the folder, spawns the harness as its detected absolute path with `harness.start()` as arguments, in that folder, through `spawnFor(contents, request)` (the pty spawn defaults and the owner registration that `pty:spawn` also uses; it goes through the restarting pty client, so a start after the host died starts a new host), then saves the session. On any failure it kills the pty if it was spawned, removes the folder it created and returns `{ status: 'refused', message: 'Could not start <name>: <error message>' }`; `state.json` is untouched. No initial prompt from the Sessions header or the `+` of a workspace row.
  - **In a workspace**: with `options.workspace` (`{ project, path }`), `sessions:start` refuses a project that is not in the state (`<path> is not a project in Cockpit.`) and a path that is not one of the project's linked worktrees according to `listWorktrees` (`<path> is not a workspace of <project name>.`; the main working tree is not a workspace; a `WorkspaceError` is a refusal too), nothing spawned. It runs the harness in the worktree, creates no folder under `$COCKPIT_HOME/sessions`, and stores the session with `project` set to the repository root. A failed start never removes anything in the worktree: only a folder the call created is removed. `options.prompt` is trimmed and passed to `harness.start(prompt)`, a blank one meaning none.
  - **Workspace sessions in the sidebar**: a workspace row has a "Start session in <name>" `+` button next to its "…" button (shown on hover and focus), with the same menu as the Sessions header (`src/renderer/components/start-session-menu.tsx`: fetched on each open, one disabled `Detecting agent CLIs…` item until the first answer, `No agent CLI found` when none). Its sessions are listed under the row, newest first, with "Ended" as in the Sessions section, which lists only the sessions without `project`. A refused start shows in the Projects message slot, cleared by the next successful start. The New workspace dialog has an "Agent" select (`None`, then the detected harnesses, fetched when the select first opens) and a "Prompt" field, disabled while Agent is `None`: Create makes the worktree, then starts the session in it and opens its page; a failed start keeps the workspace and shows its message in the Projects slot.
  - **Ending with the workspace**: once `workspaces:remove` succeeds (not at the uncommitted-changes step) or a project is removed, the renderer kills the running sessions of that workspace or project (`endSessions` in the store). Their entries stay in `state.json` and are hidden while the workspace is not listed; listed again (a project added again, a workspace re-created with the same branch, which reuses its path and continues its count), they show as "Ended". Workspaces removed outside the app leave their sessions running, hidden, until the page ends.
  - **Renderer**: the Sessions section of the sidebar has a "Start session" (`+`) menu of the detected harnesses, fetched each time it opens ("No agent CLI found", disabled, when none), the inline refusal under the header (replaced by the next refusal, cleared by the next start), and the sessions as links, newest first, with an "Ended" label unless the session is running. `src/renderer/components/live-terminals.ts` is the one module-level store of live xterm.js instances, shared by sessions and the terminal tabs: `createLiveTerminal(start)` makes an instance (with its fit addon) started at 80 x 24, subscribed to `pty.onData`/`onExit` before `start` is called, and `closeLiveTerminal` kills its pty and disposes it. Session terminals are never closed; the session page (`/sessions/$sessionId`) moves the instance's element into its container and out again (through `Terminal`, as the terminal tabs do), so navigating inside the app never kills the agent. Input and resizes are forwarded to the pty while it runs; an exit writes `[Process exited with code N]`, and a pty host crash ends every running session the same way (`exitCode: null`, so `[Process ended]`, and the entry shows "Ended"). A session the store does not hold (previous launch, reload) shows "This session has ended." and its directory; an unknown id shows "Session not found.". A reload, a window close or a quit ends the sessions (see "Sessions end with their page"); the folder stays and no output is kept.
  - **Built assets use absolute paths.** electron-vite forces `base: './'` for a production build, whatever the config says, so a nested route such as `/sessions/<id>` loaded its assets from `/sessions/assets/` (404) on a reload. A small `post` plugin in `electron.vite.config.ts` sets `base: '/'` after it.
- **Runtime tests**: no version ships with a risk of crashing at runtime. `build` and `typecheck` are not enough: `test` (vitest + Playwright, in `test/`) launches the app the four ways it runs, the `dev` script, the built app, the packaged `Cockpit.app` and the packaged app launched with launchd's minimal environment (as from the Finder or the Dock; `open` would pass on the caller's environment), and checks that each one renders, keeps Node out of the renderer, logs no error and keeps running. Every feature's tests are split across the four launches:
  - **Split rule.** A feature's full block (every case: dialogs, refusals, edge cases) runs once, in the built app. Each other launch mode runs one smoke path per feature, a single case that goes through the feature's IPC end to end (the stubbed picker or the page, then the main process, then the disk). The launchd-environment mode keeps only the smoke paths that spawn git or a shell (terminal AC12 is its shell test), since its point is the minimal environment and not the code paths. A mode-specific check runs in every mode it applies to. These are the checks on what differs between the launches: the home page and version, Node out of the renderer, the color scheme, reload, the background switch, the data folder, the output from the first line, `window.api.pty` spawn and echo, `getShellPath`, "logs no error and keeps running", the navigation guard, the node-pty prebuilds. A feature added later gets a full block in the built app and a smoke path in the other modes.
  - **Principle.** Keep the suite as fast as possible without losing coverage. An assertion runs in every launch mode only when what it checks differs between modes, and once otherwise. A behaviour is tested at the lowest level that can observe it: a package's vitest tests before Playwright. No fixed pause where a wait on a condition works.
  - Test launches stay unnoticed. Three variables, read by the main process before `ready` and honoured in the packaged app too: `COCKPIT_TEST_BACKGROUND=1` (macOS accessory policy, so no Dock icon and never the frontmost app; windows are never shown and keep rendering as if visible), `COCKPIT_USER_DATA_DIR=<dir>` (sets `userData`) and `COCKPIT_HOME=<dir>` (where worktrees and session folders live, see Workspaces in the sidebar and Sessions). The tests set all three on every launch, with a fresh `mkdtemp` folder removed after the app closes (`COCKPIT_HOME` is a folder inside it; only the test of its default leaves it unset or empty, with a `HOME` of its own). The app's own data must therefore live under `app.getPath('userData')`, so the variable isolates it, and its worktrees and session folders under `COCKPIT_HOME`, so no test creates one under the user's `~/.cockpit`.
  - **Stopping a launch.** `stopGroup` sends `SIGTERM` to the launch's whole process group and waits until no process of the group is alive, not only for the spawned child to exit (Electron's helpers can outlive `bun run dev` and still write in the data folder, which made `rmSync` fail with `ENOTEMPTY`). It sends `SIGKILL` to the group after 10 s and throws an error naming the group after 20 s. Every launch's `close()` goes through it.
  - The launch without the switch (visible window, `Foreground` app) runs only in CI, where no one's focus is at stake: `CI` reaches the tests through `turbo.json`. Do not set `CI` locally to run it.
  - **Folder picker stub**: the tests launch the app with the Node inspector (`--inspect=0`; `--inspect <free port>` for the dev script, which ignores 0), read the `Debugger listening on ws://…` line, connect with Node's global `WebSocket` and call `Runtime.evaluate` with `includeCommandLineAPI: true`, which exposes `require`, to replace `require('electron').dialog.showOpenDialog` in the main process. The app has no test hook for it. Keep `--inspect` usable in test builds, like the remote debugging port: it depends on Electron's `EnableNodeCliInspectArguments` fuse (on by default, untouched by `electron-builder.yml`), so a later fuse hardening must keep test builds able to use it. The helper disconnects the inspector before stopping the process group, since a connected inspector can hold the process at exit.
  - Playwright is maintained by Microsoft and widely adopted. The tests do not use its Electron launcher (`_electron.launch()`, labelled experimental): it runs the app's main script before it returns, so output written during startup never reaches the test. They spawn the app themselves with `--remote-debugging-port=0`, attach the output listeners at once, read the port from Chromium's `DevTools listening on ws://127.0.0.1:<port>` line on stderr, and attach with `chromium.connectOverCDP`. The session's `output()` therefore holds everything the app wrote from its first line. Before its first reload, `attach` waits until the page is on the app's URL and loaded: the window's target starts as `about:blank` while its first navigation is pending, and a reload racing it never completes. The attach goes through Chromium's remote debugging port, so never disable it in test builds.

## Workspaces (`packages/workspaces`)

Pure Node, consumed as TS source like `packages/pty`, with no `electron` import (a test checks it). Five functions: `findRepositoryRoot`, `listBranches`, `listWorktrees`, `createWorktree`, `removeWorktree`. Each takes an optional `env` used to run git, so the caller can pass the login-shell environment.

- **A package called by the main process, not a CLI.** Checked on 2026-10-19 against the source of Superset, Orca, Emdash, Vibe Kanban and Claude Squad: none of them has its app call its own CLI. Errors are typed (`WorkspaceError` with a string `code`, which survives IPC). The main process wires them (see Workspaces under the desktop app).
- **`execFile('git', …)` on the user's git, no git library.** Never through a shell. The git manual guarantees that the output of `git worktree list --porcelain` stays stable. Against the libraries: simple-git has no worktree API and one de facto maintainer; dugite ships its own git binary, which would have to be signed; isomorphic-git has no worktrees; nodegit's last stable release is from 2020. Typed errors come from pre-checks and exit codes, never from git's localized messages.
- **git 2.36 or later**, checked at runtime by every public function (`GIT_MISSING`, `GIT_TOO_OLD`): `listWorktrees` parses `git worktree list --porcelain -z`.
- **Layout**: `<root>/<project>-<hash>/<branch>`, where `<project>` is the basename of the main working tree and `<hash>` the first 8 hex characters of the SHA-256 of its path (deterministic, stateless, no collision between two repositories with the same name). A branch with a slash nests (`feature/login`). The root is a parameter: choosing the real one is the app's job.
- **`listBranches(repo, { env })`** gives `{ local, remote, defaultBase }` from `git for-each-ref` (symbolic refs skipped, so no `origin/HEAD`), local branches and `origin/*` only, with no fetch. `defaultBase` is `origin/D` when it exists, else the local `D`, else `null`, where `D` is the branch `refs/remotes/origin/HEAD` points at or, without it, the one checked out in the main working tree.
- **`INVALID_BRANCH_NAME`**: `createWorktree` throws it when `git check-ref-format --branch` refuses the name or rewrites it (`@{-1}`). Calls for one repository run one at a time (a chain of promises per repository root), so of two creating the same branch the second gets `BRANCH_EXISTS` and the winner is intact.
- **Removal and `force`.** A dirty worktree is refused (`DIRTY_WORKTREE`) unless `force` is set, which skips that check and runs `git worktree remove --force`: it exists for a caller that has asked the user to confirm. A locked worktree is refused either way. A branch is deleted only with `git branch -d`: unmerged, squash-merged included, gives `BRANCH_NOT_MERGED`, with the worktree removed and the branch kept; there is no way to force the branch. `createWorktree` does use `git worktree remove --force` and `git branch -D`, but only to roll back what the call itself created, so a failed creation leaves nothing behind (all-or-nothing).

## Harnesses (`packages/harnesses`)

Pure Node, consumed as TS source like `packages/workspaces`, with no `electron` import (a test checks it) and no runtime dependency. The main process wires it for sessions (see Sessions in the desktop app); worktrees and the other functions are not wired yet.

- **API**:
  - `harnesses`: the catalogue, three `Harness` entries in this order: `claude-code`, `codex`, `opencode`. Each has `id`, `name`, `binary`, `start(prompt?)` (interactive, in the spawn's cwd), `continueLast`, `resume(sessionId)` (argv arrays) and `sessions(env)`, which gives the location and format (`jsonl` or `sqlite`) of the harness's session store, honouring `HOME` and the relocation variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME`; an empty one counts as unset). It reads nothing. The catalogue is deep-frozen (the array, each entry and its `continueLast`; the types are `readonly`), so callers share it and none can change it for the others: a write throws a `TypeError`.
  - `detectHarnesses(env, { timeoutMs })` (default 10 000 ms): serializable `{ id, path, version }` records, in catalogue order, so they can cross IPC.
- **Only verified harnesses are listed.** Verified means official docs, the CLI's own `--help` or output, or the official open source code at a release tag. Each fact carries its source as a comment in `src/catalogue.ts`. Checked on 2026-10-20 against Claude Code 2.1.304, Codex 0.163.0 and OpenCode 2.0.31. These CLIs release weekly and the tests use stubs, so nothing catches a renamed flag: re-check the sources when updating an entry.
  - Codex's session path comes from its source, not its docs.
  - OpenCode's docs still describe the 1.x storage; the 2.x path rests on `opencode debug paths`.
- **Left out (COCKPIT-43)**, for what was missing:
  - **Cursor CLI**: session storage is not documented and the CLI is closed source; the path was only found in the shipped binary. Its binary is now `agent`, with `cursor-agent` kept as a legacy alias.
  - **Kimi**: the legacy `kimi-cli` is archived and its `kimi` no longer runs an agent. Its successor Kimi Code CLI installs the same `kimi` binary but cannot take an initial prompt in interactive mode; detection would also have to tell the two apart.
  - **Mistral Vibe**: left out by decision. 3.0 (Rust rewrite) shipped on 2026-10-19 and its session store layout is only in the source.
- **Detection rules**:
  - The package walks `env.PATH` itself: the first executable regular file named after the binary wins (symlinks followed). Empty and relative entries are skipped, as are directories and non-executable files.
  - It runs `<path> --version` with the given `env`, in its own process group, all harnesses in parallel. Exit 0 means installed, with the first `x.y.z` (optionally with a pre-release suffix) of stdout as `version`, or `null` when there is none.
  - A non-zero exit, a signal, a spawn failure or a timeout means not detected. On timeout the whole group gets `SIGKILL` and detection settles without waiting for `close`, as a background child can hold stdout open. It never rejects.
- Out of scope: combining an initial prompt with a resume, prompts that start with `-` (passed as is, not verified), minimum versions, `--version` caching, non-macOS paths.

## Tests and validation

- **CI** (`.github/workflows/ci.yml`): on every pull request and every push to `main`, one macOS job runs `bun turbo run build typecheck lint test`. macOS because the desktop app is packaged for macOS and its tests open windows. The repository is public, so GitHub-hosted runners cost nothing.
  - **Lint**: the `lint` step runs oxlint on all 7 workspaces and fails on any `correctness` finding. A scripted check at build time, logged in the pull request, verified that a deliberate `debugger;` fails it in each workspace and that a `useEffect` with a missing dependency fails it in the desktop renderer; the vitest tests in `.github/scripts/plane-sync/test/lint.test.ts` only read files (the lint scripts, `turbo.json`, `ci.yml` and this file), because CI runs `lint` and `test` in parallel.
- **Plane sync** (`.github/workflows/plane-sync.yml`, script in `.github/scripts/plane-sync`): when a pull request targeting `main` is closed and `merged` is true, an `ubuntu-latest` job runs the script with Bun (no install step). The PR title, the head branch and the secret `PLANE_API_KEY` reach it through `env`, never through an expression in a `run:` line (the title and branch are user input).
  - **Ticket id**: the last `COCKPIT-N` of the title (case-insensitive), else the `cockpit-N` the branch starts with. With neither, nothing is sent to Plane and the run succeeds.
  - **Done and unblock rules**: the ticket goes to the project's single state of group `completed` (Done). Dependents in any other state are left alone.
  - **Idempotent**: a ticket already in Done and dependents already past Backlog get no request, so re-running a PR changes nothing.
  - **Failure**: `PLANE_API_KEY` is required only when the pull request carries a ticket id (one without exits 0 without it). An empty key then, or a non-2xx answer from Plane, stops the run with a non-zero exit code and a message naming the variable, or the method, path and status.
  - Plane REST API v1 (`X-API-Key`): v2 has no relations endpoint (checked on 2026-10-21), and v1 is not being switched off. A fork's pull request gets no secret, so its run fails; the repository has one contributor.
- **`main` is protected** by a ruleset: changes go through a pull request, the CI `check` job must pass on a branch up to date with `main`, and force pushes and deletion are blocked. The rule applies to administrators too.

Terminal: a typed command shows its output. Terminal tabs (smoke path (c), dev server and packaged app, not the launchd-environment mode): three terminals in `A | (B / C)`, "Close terminal" on C ends its shell and gives the keyboard to B, not A, then a second tab is opened and closed and its shell ends, then Home and back keeps A and B alive with their output and B takes a command, then the pty host is killed: the remaining terminals show `[Process ended]` and a new tab runs a command. The built app covers that scenario in its full block (closing and the host kill). Sessions, with the stub fake login shell: picking Claude Code runs the stub in a new folder under `COCKPIT_HOME`, lists the session and stores it; a new workspace with Claude Code and a prompt runs the stub in the worktree with the prompt as its argument, lists the session under the workspace and stores it with its `project`. The dev server runs them on a launch of its own; the packaged app runs them in the first launch of the restart test below. The launchd-environment mode runs the two paths that spawn git (projects and workspaces) and the terminal shell test, and no other terminal test, and has no sessions smoke path: its point is the user's real login shell, where a session would run a real CLI.
  - **Outside the four modes.** A dedicated built-app launch with a fake login shell whose `PATH` holds no git shows `git is not installed`. The packaged app also restarts on the same folder (`state.json` unchanged, nothing set aside), keeps a project across a restart on the same folder and removes it, reads a `state.json` without `projects` as no project and leaves it unchanged, sets a corrupted file aside and starts, exits with code 1 and no window on a newer-version file, and does the same on an unreadable one (a folder named `state.json`), leaving the file alone. A dedicated packaged-app launch quits the app as Cmd+Q does (`app.quit()`) with two shells open and checks both are gone. "No window" is checked through the window traces Chromium writes in the data folder (`Preferences`, `Local Storage`, `Session Storage`, `Cache`), absent after those exits; a guard checks that a normal packaged start does create them, so an Electron that stops writing them fails the guard instead of passing the check silently. A built-app launch without any CLI shows the disabled "No agent CLI found"; one with `COCKPIT_HOME` unset or empty and `HOME=<tmp>` puts the session folder under `<tmp>/.cockpit/sessions`; the packaged app restarted on the same folders lists the earlier sessions as "Ended", newest first, opens one as ended, and leaves `state.json` and the folders alone.
  - **Navigation guard.** In the three isolated-shell modes, a page script that navigates to `app://other/`, `https://example.com/` or an existing `file://` URL leaves the page URL, the heading, the shell's process and the terminal as they were, with no console error (but Chromium's refusal of the `file://` URL), page error or main-process error, and the only console error allowed is `Not allowed to load local resource` for the exact `file://` URL tried; a real Finder drop cannot be produced over CDP, so it is not tested.
- `packages/pty` (vitest, plain Node): the host and the client wired through in-memory ports, with the real node-pty, including the restart after the host died (a new host forked by the next `spawn`, spawns issued together sharing it, ids never reused, write, resize and kill on an old id doing nothing to the new sessions, what a dead host still sends ignored, a `spawn` still waiting rejecting when its host dies).
- `packages/shell-env` (vitest, plain Node): `resolveShellEnv` against fake shells (startup noise, multi-line values, timeout, missing or failing shell, no passwd entry and no shell found, an unreadable home directory, a background process holding stdout, injected and removed variables).
- `packages/state` (vitest, plain Node): `loadState` on a fresh folder per case: missing file and folder, read back without a rewrite (absent `projects` and `sessions` read as `[]`), each corrupted shape set aside (malformed `projects` and `sessions` included), newer version, unreadable file (`EISDIR` for a folder, `EACCES` for a file without read permission, nothing renamed, created or removed), leftover `.tmp`; the backup as a copy when the hard link fails and under the first free `-<n>` name when taken; `saveState` call order (write, fsync, rename, open and fsync the folder, with `node:fs` partially mocked); `addProject`, `removeProject`, `addSession` and `sessionName` (per workspace and outside any project); sessions without `project` read as outside any project.
- `packages/workspaces` (vitest, plain Node): the five functions against the real git (`listBranches` on a clone of a temporary repository, `force` removals, two concurrent creations), on temporary repositories and roots under `os.tmpdir()`, with an env that ignores the user's git config.
- `packages/harnesses` (vitest, plain Node): the catalogue's exact values (ids, argv, session stores with and without the relocation variables), its frozen state (a push or an assignment throws a `TypeError` and changes nothing), and `detectHarnesses` against `#!/bin/sh` stubs in temporary folders (versions, `PATH` lookup rules, a failing `--version`, a stub that never exits with a background child holding stdout, no version printed, the env passed to the stub, an unrunnable file). No real CLI is run.
