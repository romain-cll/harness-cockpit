# AGENTS.md — cockpit

**cockpit** is a provisional working name. It appears in the desktop app (`Cockpit`, `com.cockpit.desktop`).

## What belongs in this file

Every session loads this file whole (Claude Code truncates at 150,000 characters), so it stays short; a test fails at 40,000.

- Keep: rules and conventions; technical choices with their verified facts (date, source), exit cost and trigger to revisit; pitfalls the code does not show.
- Leave out: feature behaviour (UI copy, messages, IPC lists, refusal texts, per-feature flows) and test case inventories. The code and the tests state them.
- A ticket adds a line only for a new package or app, a new rule, a new technical choice or a new pitfall.

## Rule #1: no over-engineering

Do not add any abstraction, package or app beyond what this file describes. When in doubt, do the simplest thing.

## Technical choices: long-term viability first

Choose a tool, library or framework on long-term viability: who maintains it (organization or single person), release activity, real adoption, compatibility with the stack, cost of leaving it. Setup speed and amount of configuration are no argument. Back the choice with verified facts.

## Language

Everything in this repository is in English: code, identifiers, comments, docs, branch names, commit messages, PR titles and descriptions.

## Product

A desktop application that drives agent CLIs (Claude Code, Codex, OpenCode…) through node-pty, following Superset's projects / workspaces model. Differentiators: sessions outside any project; artifacts on storage you own; usage statistics.

UI so far: projects and workspaces, the workspace page (its agent sessions and shells as tabs of split panes), sessions, right bar (changes, commit, push, pull request), open in editor/terminal.

Artifacts, stats, cloud backend, web app, mobile: none without an explicit request. The daemon is a package, not an app.

## Monorepo

- No business logic in `apps/`: everything lives in `packages/`, apps only wire things (`apps/cli` is a one-line entry over `@cockpit/daemon/cli`). No other app without an explicit request; `apps/cli` is COCKPIT-56's CLI and nothing else.
- Bun (package manager, workspaces, scripts) + Turborepo, TypeScript. Node 22+ for the tooling; the desktop app runs on Electron's Node (24 in Electron 44). A native module (`node-pty`) must be built for the runtime that loads it.
- Set up by hand, without `create-turbo`: workspaces `apps/*`, `packages/*`, `.github/scripts/plane-sync`; `turbo.json` tasks `build`, `dev`, `test`, `typecheck`, `lint`; `tsconfig.base.json` extended by every package; one root `.oxlintrc.json`. `workspace:*` internal dependencies; packages consumed as TS source, no per-package build; `vitest`.
- `test` is never cached (its result depends on the machine: Electron binary, login shell; Turbo shares its cache across git worktrees); `lint` is never cached, so a `.oxlintrc.json` change is never hidden.
- Linting is oxlint: a check-only `"lint": "oxlint"` script per workspace, no `--fix`, run by `bun run lint` through Turbo. Config: default plugins plus `react`, `correctness` as `error`, `routeTree.gen.ts` ignored (git-ignored paths skipped); no type-aware rules, other categories or formatting. Root `devDependency`.
  - Why (checked 2026-10-21): built by VoidZero (Evan You's company: Vite, Vitest, Rolldown), acquired by Cloudflare on 2026-06-04 with the projects staying MIT; weekly releases (1.0.0 on 2025-06-10, 1.89.0 on 2026-10-19); about 16.2 M downloads a week, 23,159 stars on `oxc-project/oxc`; own Rust parser, the only one of the three aligned with TypeScript 7, which the repo uses. Single npm publisher (`boshen`); code in a company organization.
  - Biome: community-run `biomejs` org, about $30k a year from sponsorship, 11.0 M downloads a week, 25,979 stars, own rule names and config (medium exit cost). ESLint (OpenJS Foundation, 96.1 M a week, 27,569 stars) + typescript-eslint (55.6 M a week, 16,435 stars): 8.72.0 declares `typescript >=4.8.4 <6.1.0` and imports TypeScript's JS API, which TypeScript 7 lacks, so it needs TypeScript 6 alongside until TS 7.1 support lands.
  - Exit cost low: its rules are ports of ESLint, typescript-eslint, unicorn and react rules under the same names. It ships weekly and `^1` lets a new correctness rule fail CI after a lockfile update; the lockfile pins CI's version, so only a deliberate `bun update` does.
  - Tests must not run the linter (CI runs `lint` and `test` in parallel); the deliberate-error checks (a `debugger;` fails in each workspace, a `useEffect` with a missing dependency in the renderer) were a scripted build-time check, logged in the PR.
- Layout: `apps/cli` (`cockpit` binary), `apps/desktop` (Electron), `packages/daemon` (owns every pty), `shell-env` (login-shell environment), `state` (JSON app state), `workspaces` (git worktrees), `harnesses` (agent CLIs), `launchers` (editors, terminal apps), `github` (pull requests through `gh`), `.github/scripts/plane-sync` (repo tooling run by a workflow, consumed by nothing else, a workspace only so Turbo runs its tests in CI, no runtime dependency).

Commands: `bun install`; `bun run build|test|typecheck|lint` (turbo; `test` launches the desktop app: needs a desktop session); `bun turbo run build test typecheck` (several tasks in one pass); `bun run --filter @cockpit/desktop dev|package|test` (hot reload | `Cockpit.app` in `apps/desktop/release/` | dev, built and packaged app).

## Desktop app (`apps/desktop`)

- Stack: Electron 44, electron-vite, electron-builder, React 19, TanStack Router (file-based). electron-builder rather than Forge: Forge has no Bun support and its Vite plugin leaves `node_modules` out of the package, breaking node-pty. electron-vite has a single maintainer but is a thin layer over Vite: if abandoned, replace it with Vite and a dev script (packaging does not depend on it).
- UI: Tailwind CSS 4, shadcn/ui on Base UI (`base-mira`), lucide, the system font. Tailwind Labs' team shrank in January 2026; releases continue. shadcn/ui is no runtime dependency (its CLI copies source we own); Base UI is maintained by MUI, shadcn's default since July 2026. `cn` is 0.x since September 2026: if abandoned, `clsx` + `tailwind-merge`, same API.
- `src/`: `main/` (window, `app://` protocol, IPC), `preload/` (`window.api` only), `shared/` (`Api` types), `renderer/` (`routes/`, `components/` + shadcn `ui/`, `styles.css`).
- Renderer boundary: no `electron` or Node import in the renderer; only `window.api`, typed by `Api` in `src/shared/api.ts`, reaches the main process. A future web app (TanStack Start) implements the same `Api` over HTTP; no web app or shared UI package until then. `Api` declares types like `ChangedFile` and `FileDiff` itself: importing them pulls a package's Node types into the renderer's typecheck. Modules a vitest test imports directly (`project-colour.ts`, `parsePatch` in `diff-view.tsx`, `workspace-layout.ts`) must not import through `@/`; `pull-request-reads.ts` uses a cast.
- Security: `contextIsolation` and `sandbox` on, `nodeIntegration` off; a sandboxed preload cannot be an ES module, so it is bundled as CommonJS (`index.cjs`). The renderer is served from `app://renderer`, never `file://`, with a CSP in `index.html` (real URLs for the router, as on the web). New windows are denied (`https` goes to the system browser); navigation off the app origin is blocked, comparing origins rebuilt from protocol and host (`URL.origin` is `"null"` for `app:`, which would let `app://other/` through). `about:blank` is not covered (Chromium commits it synchronously, with no `will-navigate`; only the app's own code gets there). `navigateOnDragDrop` is off. Every privileged IPC handler ignores a sender frame that is not the app's page (`isFromApp`); an invoke rejects.
- Dependencies: what the bundles import goes in `devDependencies` (electron-vite bundles it); only unbundleable native modules (node-pty) go in `dependencies`, which electron-builder ships and rebuilds.
- Styling: Tailwind utilities with the semantic tokens of `styles.css`, never raw colors or `dark:` color overrides. Tokens come from the Figma "Cockpit" file, page "Redesign — Linear direction", collections "Theme v2" and "Theme v2 / Light" (COCKPIT-65), in hex; radius scale 6, 8, 10, 12 px as fixed values, not `calc` of `--radius`. In the sidebar and the right bar no font weight above 400, Lucide stroke width 1.25. Diff and merged-state colors are tokens too (`--diff-added-foreground`, `--diff-removed-foreground`, `--diff-hunk`, `--status-merged`). Prefer a shadcn/ui component to custom markup: `bunx --bun shadcn add <name>` from `apps/desktop` (`components.json` is there; the `@/` alias in its `tsconfig.json` is for the CLI), move the packages it adds to `devDependencies`, add one only when a feature uses it.
- Right bar: the right column of a workspace page is a `div` with role `complementary` named "Right bar", never an `<aside>` (the left sidebar is the only one). Its state (`{ open, tab }`) is module-level. The bar reads git, watches the worktree and runs `gh` only while mounted, so nothing runs while it is closed, a window focus included. Its buttons carry `transition-none`: shadcn's `transition-all` leaves a color mid-transition when read right after a theme or tab change.
- Theme follows the system through `prefers-color-scheme` (driven by `nativeTheme`). Dark tokens live under `@media (prefers-color-scheme: dark)`, not `.dark` (move a CLI-added block there). A future theme setting sets `nativeTheme.themeSource`.
- Window chrome: macOS hides the title bar (`trafficLightPosition: { x: 14, y: 16 }`); top strips drag the window (`app-drag`), interactive elements inside need `app-no-drag`; other platforms keep the native frame.
- `routeTree.gen.ts` is generated on `dev`/`build` and committed so `typecheck` works on a fresh checkout. Outputs: `dist/` (Turbo `build`), `release/`.
- Built assets use absolute paths: electron-vite forces `base: './'`, which broke nested routes on reload; a `post` plugin in `electron.vite.config.ts` sets `base: '/'`.
- Packaging: `package` builds the CLI, then an ad-hoc signed `Cockpit.app` with the CLI at `Contents/Resources/bin/cockpit` (`extraResources`). Developer ID signing, notarization, installers, auto-update: later, on request. Since Electron 42 its binary downloads on the first `require('electron')`; `dev` runs `install-electron` first.
- Login-shell environment: an app started from the Finder or Dock gets launchd's minimal `PATH`, so the main process resolves the login shell's environment once per launch (`shellEnv`, `src/main/shell-env.ts`) and every child process (git, `gh`, `open`, harness detection) spawns with `await shellEnv`. The renderer only gets `PATH` (`window.api.getShellPath()`).
- Data locations: app data under `app.getPath('userData')`; worktrees, session folders and daemon files under `$COCKPIT_HOME`: `~/.cockpit` packaged, `~/.cockpit-dev/<folder>` unpackaged (its `userData` is `<that>/user-data`). `<folder>` is `devFolderName` (`src/main/dev-folder.ts`) of the worktree root: basename sanitized to `[A-Za-z0-9._-]` and cut to 20, plus `-` and 8 hex characters of the SHA-256 of its path, at most 29 bytes so `daemon-1-<build>.sock` fits macOS's 103-byte socket path limit. Worktrees and session folders are the user's work, not app data: the space in `Application Support` breaks some tools, and AppCleaner-type uninstallers would wipe uncommitted work.
- Single instance: `app.requestSingleInstanceLock()` goes right after `app.setPath('userData', …)`, since Electron ties the lock to `userData`; a loser calls `app.exit(0)` and touches nothing.
- Workspace panes are rendered flat (one list keyed by pane id, placed by percent boxes; each pane's terminals stacked under its tab bar, the unselected ones `invisible` at full size) so a split, close or tab switch never remounts a view. Keys typed before `spawn` resolves are held and written in one write once the id is set; the tty buffers them until the shell reads, so its startup loses nothing.
- The pane layout is not saved (COCKPIT-70): after a reload or restart a workspace's running sessions and shells come back as the tabs of one pane, in creation order. A shell is spawned with its `workspace` so the daemon's list maps it back; a shell spawned without one is not shown. The root loader does not await the restore: a daemon that does not answer (`SIGSTOP`) must not keep the page from opening.
- xterm.js pauses its renderer while its element is out of the page, and a fit or scroll handled meanwhile uses the old size: a re-attached terminal draws first, then fits and restores its scroll. Base UI's modal menus make the page inert and return focus to their trigger, so a menu action that moves the keyboard (new tab, closed pane) gives it back to the terminal once the menu has closed.
- Late spawn ack: a spawn resolving after its page navigated or was destroyed kills the terminal and throws `PageGoneError`; `pty:spawn` catches it and returns `-1`, so Electron logs no `Error occurred in handler` (tests count it as an error) and a reload leaves no orphan shell. Only `commands` terminals (a teardown) end with their page: `did-navigate`, window destroyed, or `did-fail-load` with any code but `ERR_ABORTED` (-3) (an error page never commits). `shell` and `session` terminals never do.
- Spawn defaults (`withSpawnDefaults`, `terminalEnv()`): the `SHELL` of `await shellEnv` (`/bin/zsh` if unset) as a login shell (`-l`, default shell only), the home directory, `await shellEnv` minus the inherited `COCKPIT_SESSION_ID`, `COCKPIT_WORKSPACE_PATH`, `COCKPIT_SOCKET`, `ELECTRON_RUN_AS_NODE`, plus `TERM=xterm-256color`, `COLORTERM=truecolor`, `COCKPIT_SOCKET` and the CLI's folder first on `PATH`. A request's own `env` replaces all of it.

## Daemon and terminals (`packages/daemon`)

Pure Node, importing neither `electron` nor `apps/` (a test checks it). Runtime dependencies: node-pty (native, shipped by electron-builder), `@xterm/headless` and `@xterm/addon-serialize` (bundled). `apps/desktop` only wires it: `src/main/daemon.ts` is the entry (`<Electron binary> <bundle> --cockpit-daemon <build>` with `ELECTRON_RUN_AS_NODE=1`; test teardown looks for that marker), `src/main/index.ts` connects and forwards `pty:*`. `@cockpit/daemon/cli` pulls neither node-pty nor xterm.

- It owns every pty and outlives the app: quitting, reloading, updating, closing the window or `SIGKILL` of the app ends no shell or agent. It never idle-stops, no login service starts it (launchd is out of scope), the app starts it on demand.
- Files: flat in `$COCKPIT_HOME` as `daemon-<protocol>-<build>.{sock,token,pid,log}` (protocol `1`); `.sock` and `.token` mode `0600`; the token (32 random bytes, hex) is new at every start and written by rename; `.log` is kept. The build is the first 12 hex characters of the SHA-256 of the daemon bundle, `process.versions.electron` and node-pty's version, so an update changing none keeps the running daemon; `COCKPIT_TEST_DAEMON_BUILD`, when non-empty, replaces it in every build.
- `RunAsNode` fuse: needed by the daemon (on by default, untouched by `electron-builder.yml`); test builds also need `EnableNodeCliInspectArguments` and the remote debugging port; fuse hardening (Developer ID, notarization) must keep them. Why the app's Electron binary rather than a bundled Node (checked 2026-10-28): no second runtime to ship, sign, notarize and patch; node-pty's N-API prebuilds load under it; VS Code's `code` CLI does the same. Exit cost: one spawn call. After an update only node-pty's `spawn-helper` is read again.
- Superseded rule: an app connects to every `daemon-1-*` socket (older builds first, so terminals list in creation order), saying `hello` with its build. A daemon hearing another build keeps its terminals, refuses its `spawn`s and exits once empty: new terminals run in the new build's daemon. Other protocols' daemons are left alone.
- Lazy restart: a dead daemon ends its terminals with `exitCode: null`; the next spawn or session start starts a new one. Terminal ids are the main process's counter, never reused across daemons. No crash-loop handling. A daemon that cannot start or does not answer in 5 s never stops the app: one stderr line, the window opens, projects and workspaces keep working.
- Transport: HTTP over the Unix socket (`Upgrade: cockpit-1`, `Authorization: Bearer <token>` compared with `timingSafeEqual`; `401` with an empty body before anything else is read), then one JSON object per line. Output goes daemon, main, renderer; a `MessagePort` is impossible (the daemon is no Electron process of the app) and no measurement shows the main process as a bottleneck. Trigger to move: typing latency, or a saturated main process, with several terminals active. HTTP rather than JSON-RPC: no dependency either way, `curl --unix-socket` ships with macOS. Token next to the socket (`${COCKPIT_SOCKET%.sock}.token`), no `COCKPIT_TOKEN_FILE`. `POST /session-events` is the status endpoint for hooks and `cockpit setup`.
- Restoring: per terminal a headless xterm, serialized on `attach` (memory only); view and daemon both keep `SCROLLBACK` (1000 lines). Output chunks carry a per-terminal sequence number, so `attach` plus later `data` events lose and duplicate nothing.
- Ending a terminal: SIGHUP, then SIGKILL to its own process 1 s later if no exit was seen (timer `unref()`ed). Why: bash 3.2 (macOS `/bin/sh`) drops a SIGHUP arriving during startup and a script may trap `HUP`, so a lone SIGHUP could leave an unlisted process running, to return as a tab after a reload (COCKPIT-64). The SIGKILL reaches neither children nor the group. Each per-terminal node-pty call is guarded (bad sizes, exit races).
- xterm.js (`@xterm/xterm` `^6.0.0`, `@xterm/addon-fit` `^0.11.0`, in the daemon `@xterm/headless` `^6.0.0` and `@xterm/addon-serialize` `^0.14.0`; stable rather than the 6.1 beta line VS Code tracks): `xtermjs/xterm.js` (organization), MIT, 21,285 stars, maintainer tyriar, a VS Code dependency; about 3.9 M / 3.4 M downloads a week (xterm / addon-fit); stable releases are rare (6.0.0 on 2025-12-22), betas continuous. Checked 2026-10-20. Exit cost: one component.
- node-pty: Microsoft (`microsoft/node-pty`, VS Code's terminal backend), about 2.5 M downloads a week, 2,050 stars (checked 2026-10-19). Pinned exactly to `1.2.0-beta.15`: 1.1.0's macOS `spawn-helper` lacks the execute bit (every spawn fails with `posix_spawnp failed`), 1.2.0 fixes it; move to 1.2.0 once published. Pinned in both `apps/desktop` (shipped by electron-builder) and `packages/daemon` (Bun's isolated linker resolves each workspace's own dependencies).
  - `npmRebuild: false`: node-pty is N-API, so its prebuilds load under Electron as they are. A rebuild compiled it in the shared Bun store (`node_modules/.bun/`), whose `build/` then shadowed the prebuilds for every later run: delete a rebuilt `build/`. `asarUnpack: node_modules/node-pty/**` keeps `pty.node` and `spawn-helper` runnable.

## State (`packages/state`)

The app state is one JSON file, `state.json`, in `userData`; the package does not import `electron`. A feature that stores a field adds it with a write API.

- Atomic, durable write: `state.json.tmp`, `fsync`, rename, then `fsync` of the folder so the rename survives a power loss (libuv's `fsyncSync` already does `F_FULLFSYNC` on macOS; only the folder sync was missing).
- Corrupted file: kept as `state.json.corrupt-<timestamp>` with its original bytes (hard link so `state.json` is never missing, else a copy; first free `-2`, `-3`… suffix, never overwriting), a fresh file written, a warning naming the backup. Newer version or unreadable file: touch nothing, no window, stderr message, exit 1.
- Git is the source of truth for worktrees: the state never stores what `git worktree list` can tell.
- Why JSON rather than SQLite (checked 2026-10-20): a few small records written by one process; JSON has nothing to maintain, and leaving costs one migration driven by `version`. `node:sqlite` in Node 24.22.0 (Electron 44.9.x) is "Stability: 1.2 - Release candidate": built in but not Stable, and it moves with Electron's Node. `better-sqlite3` 13.0.3 (2026-08-05): single npm maintainer (joshuawise), 7.2 M downloads a week, 7,522 stars, N-API prebuilds since 13.0.0 but still native.

## Workspaces (`packages/workspaces`)

Pure Node, no `electron` import (a test checks it). Functions take an optional `env` for git.

- A package called by the main process, not a CLI (checked 2026-10-19: Superset, Orca, Emdash, Vibe Kanban, Claude Squad: no app calls its own CLI). Errors are typed (`WorkspaceError`, string `code` surviving IPC), from pre-checks and exit codes, never git's localized messages.
- `execFile('git', …)` on the user's git, never a shell, no git library: the git manual guarantees `git worktree list --porcelain` stays stable. simple-git has no worktree API and one de facto maintainer; dugite ships its own git binary (to sign); isomorphic-git has no worktrees; nodegit's last stable release is 2020. git 2.36+, checked at runtime (`GIT_MISSING`, `GIT_TOO_OLD`): `worktree list --porcelain -z`.
- Layout `<root>/<project>-<hash>/<branch>`, `<hash>` the first 8 hex characters of the SHA-256 of the main working tree's path (stateless, no collision between same-named repositories). A workspace is a linked worktree; the main working tree is the project, never listed. Calls per repository are serialized. `createWorktree` is all-or-nothing: its rollback (`git worktree remove --force`, `git branch -D`) removes only what it created.
- Base: recorded as `branch.<name>.cockpitBase` in git config before `git worktree add` (unset in the rollback); an unresolvable base falls back to the default base, then `NO_BASE`. Untracked files reach `git diff` through a temporary copy of the index (`GIT_INDEX_FILE`). Reading never writes under the gitdir, or the watcher on it would loop: `git --no-optional-locks status --porcelain`, temporary index copies.
- `watchWorktree`: recursive `fs.watch` (FSEvents, macOS only), 200 ms debounce, also watching git metadata (commits, pushes, fetches in a terminal). FSEvents never reports what happened before its stream starts, so the start touches the mtime of every watched folder until each reports an event (2 s at most).
- `fileDiff`'s 1 MiB limit is the explicit `maxBuffer` of that git call (raising the default buffer does not change it).
- Removal: a dirty worktree is refused (`DIRTY_WORKTREE`) unless `force`, for a caller that asked the user to confirm. A branch goes only with `git branch -d`, never forced: unmerged (squash-merged included) is kept (`BRANCH_NOT_MERGED`). Push is `git push --set-upstream origin <branch>` with `GIT_TERMINAL_PROMPT=0`, never `--force`, `--force-with-lease` or a `+refspec`.
- Config (`readWorkspaceConfig`): `<main working tree>/.cockpit/config.json`, `{ "setup": string[], "teardown": string[] }`, read from the main working tree only (a worktree-only config is ignored); any other shape or key is `INVALID_CONFIG`.

## Harnesses (`packages/harnesses`)

Pure Node, no `electron` import (a test checks it), no runtime dependency, deep-frozen catalogue.

- Only verified harnesses are listed: official docs, the CLI's own `--help` or output, or official source at a release tag, each fact sourced in a comment in `src/catalogue.ts` and `src/status.ts`. Checked 2026-10-20 against Claude Code 2.1.304, Codex 0.163.0, OpenCode 2.0.31 (status: 2026-10-25, Claude Code 2.1.310). They release weekly and tests use stubs, so nothing catches a renamed flag: re-check the sources at every entry update. Codex's session path comes from its source; OpenCode's 2.x path from `opencode debug paths` (its docs describe 1.x).
- Left out: Cursor CLI (session storage undocumented, closed source); Kimi (legacy `kimi-cli` archived, its `kimi` runs no agent; successor Kimi Code CLI takes no initial prompt interactively); Mistral Vibe (by decision: 3.0, a Rust rewrite, shipped 2026-10-19; session layout only in the source).
- Detection walks `env.PATH` itself and runs `<path> --version` with the given `env` in its own process group, all in parallel, never rejecting; on timeout it `SIGKILL`s the group and settles without waiting for `close` (a background child can hold stdout).
- Status reporting (`statusLaunch`): harnesses run `cockpit status <event>` (`working`, `waiting`, `finished`), set up through argv and environment only (Claude Code `--settings`, Codex `-c hooks=…`, an OpenCode plugin file), never in the user's repo or global config. Codex runs a hook only when trusted, so the `-c` carries a `trusted_hash` from a formula taken from Codex's source, not its docs: a release changing it shows "Hooks need review" with no dot, so re-check it at each catalogue update. Out of scope: overriding `disableAllHooks`, `features.hooks = false` or an admin policy; terminal-output heuristics.

## Launchers, GitHub and shell-env

Pure Node, no `electron` import, no runtime dependency. `launchers` and `github` are packages of their own (`apps/` holds no logic, `workspaces` is about git).

- Launchers: detection only stats `<bundle>.app` in the applications folders (no `open`, Launch Services or Spotlight query, cache or editor CLIs). Runs use `open -a <absolute bundle path>`, since `open -a <name>` may pick another copy than the one detected; `execFile('open')`, never a shell. Sources checked 2026-10-25, each a comment in `src/catalogue.ts`; Warp rests on its docs only (closed source): drop it if a release breaks it.
- GitHub: `gh` through `execFile` with `GH_PROMPT_DISABLED=1`; ENOENT is `GH_MISSING`, exit 4 `GH_UNAUTHENTICATED`. An unknown check value is never passing. Risk: `statusCheckRollup` values are GitHub GraphQL enums; a new one reads as unknown until the package's list is updated.

## CLI (`apps/cli`)

The `cockpit` command line (COCKPIT-56). Its logic is `runCli` in `packages/daemon/src/cli.ts` (exported as `@cockpit/daemon/cli`; `setup`/`teardown` in `src/setup.ts`); `apps/cli/src/main.ts` only passes `process`; `bun build --compile` makes `apps/cli/dist/cockpit`. It ships at `Contents/Resources/bin/cockpit` packaged, `apps/cli/dist/cockpit` otherwise; the main process passes that absolute path to `statusLaunch`, so older sessions' hooks run the new binary against the old daemon.

- `cockpit status` always exits 0, writes nothing and gives up after 2 s: a failing hook shows an error in Claude Code and Codex, and some hooks' stdout reaches the model. Other usage errors exit 2.
- `setup`/`teardown` run each repository command in its own `/bin/sh -c`. The CLI ignores `SIGINT` and `SIGQUIT` so a Ctrl+C reaching its process group ends the child, not the CLI.
- Ending (COCKPIT-64): the daemon's SIGHUP then SIGKILL hit only the CLI's pid, and the kernel's hangup reaches only the foreground group, which an interactive login shell takes for itself, orphaning the agent or shell. So the CLI catches SIGHUP and SIGTERM, synchronously signals every process under it (`ps -axo pid=,ppid=`, whatever its group), waits up to 300 ms, SIGKILLs the rest and exits 129 or 143, before the daemon's SIGKILL. Limits: daemonized processes; macOS's `ps` only.
- Why a Bun compiled binary (checked 2026-10-28, macOS arm64, warm cache, 30 runs, median / p90, `204` from a fake daemon): the former `curl` line through `/bin/sh -c` 11.2 / 11.9 ms; Bun 1.4.3 compiled 15.0 / 16.1 ms (68 MB); Node 24 35.1 / 37.0 ms; Electron 44 with `ELECTRON_RUN_AS_NODE=1` 50.7 / 52.7 ms. `oven-sh/bun`: organization repository (Oven, acquired by Anthropic on 2025-12-02, MIT, developed in public), 96,449 stars, 1.4.0 (2026-08-20) to 1.4.4 (2026-10-22), 5.3 M npm downloads a week; it cross-compiles to Linux and Windows (COCKPIT-58, COCKPIT-59). Exit cost low: the logic is plain Node in `packages/daemon`; another build (Node SEA, Rust, Go) replaces only the compile step. Risks: +68 MB; Developer ID signing needs the same `allow-jit` entitlement as Electron's V8 for one more binary.
- Pinned Bun: the compiler is the root `packageManager` version (`bun@1.4.2`), through an exact `bun` devDependency of `apps/cli` and `bun.lock`, so updating Bun on a machine or in CI never changes the shipped CLI silently. `scripts/check-bun.ts` fails the build naming both versions on a mismatch; change `packageManager` and the devDependency together.

## CI and Plane sync

- CI (`.github/workflows/ci.yml`): every PR and push to `main` runs one macOS job, `bun turbo run build typecheck lint test` (the app is packaged for macOS and its tests open windows; the repo is public, so runners are free). `main` is protected by a ruleset: PR, CI `check` green on a branch up to date with `main`, no force push or deletion, administrators included.
- Plane sync (`.github/workflows/plane-sync.yml`, `.github/scripts/plane-sync`): when a PR to `main` is merged, its ticket (last `COCKPIT-N` of the title, else the `cockpit-N` branch prefix; none, nothing sent) goes to Done, and each ticket it blocks goes Backlog to Todo once all its blockers are Done (Cancelled does not count); idempotent. `PLANE_API_KEY` is required only with a ticket id. Title, branch and secret reach the script through `env`, never a `run:` expression. Plane REST v1: v2 has no relations endpoint (checked 2026-10-21). Fork PRs get no secret.

## Tests

- No version ships with a risk of crashing at runtime: `build` and `typecheck` are not enough. `test` (vitest + Playwright, `apps/desktop/test/`) launches the app the four ways it runs: the `dev` script, the built app, the packaged `Cockpit.app`, and the packaged app with launchd's minimal environment (as from the Finder or Dock). Each must render, keep Node out of the renderer, log no error and keep running.
- Split rule: a feature's full block (every case) runs once, in the built app; each other mode runs one smoke path per feature, through its IPC end to end. The launchd mode keeps only paths that spawn git or a shell. As fast as possible without losing coverage: an assertion runs in every mode only when what it checks differs between modes; test at the lowest level that can observe the behaviour (a package's vitest before Playwright); no fixed pause where a condition can be awaited. Checks of what differs between modes (page and version, Node out of the renderer, color scheme, reload, background switch, data folder, first-line output, pty spawn, `getShellPath`, no error logged, navigation guard, node-pty prebuilds) run in every mode they apply to.
- Tests never run a real agent CLI, `gh`, `open` or notification: `#!/bin/sh` stubs on a fake login shell's `PATH`, and `SHELL=/bin/sh` except in the launchd mode. Daemon on real sockets (short temp folders) and node-pty; workspaces on real git; harnesses, launchers, github against stubs; state, shell-env on temp folders and fake shells; `apps/cli` as the compiled binary.
- Test launches stay unnoticed. Read by the main process before `ready`, packaged app included: `COCKPIT_TEST_BACKGROUND=1` (accessory policy: no Dock icon, never frontmost; windows never shown, rendering as if visible), `COCKPIT_USER_DATA_DIR`, `COCKPIT_HOME` (a short `<data folder>/h`), `COCKPIT_TEST_APPLICATIONS_DIR`, `COCKPIT_TEST_DAEMON_BUILD`; a fresh `mkdtemp` folder per launch. The visible-window launch runs only in CI (`CI` reaches tests through `turbo.json`); never set `CI` locally.
- Guard for the default folders: a launch leaving `COCKPIT_USER_DATA_DIR` unset or empty relies on the app's default; a regression (a `||` mutated into `??` was tried) would write into the real `~/Library/Application Support/@cockpit/desktop`, and `HOME=<tmp>` alone does not prevent it (Electron's `appData` ignores `HOME` on macOS). So `launchEnv` in `test/launch.ts` throws unless such a launch has a `HOME` inside the run root, and sets `CFFIXED_USER_HOME=<HOME>`, which moves `~/Library`.
- Run root and cleanup: a global setup (`test/global-teardown.ts`) makes one `ck-` folder per run in `/private/tmp` (`COCKPIT_TEST_RUN_ROOT`), folder prefixes at most 3 characters so socket paths fit. The daemon outlives the app: `close()` kills the home's daemons by `.pid`, the global teardown every daemon under the root with `--cockpit-daemon` on its command line (other runs' are left alone). `stopGroup` waits until the whole process group is gone (`SIGTERM`, `SIGKILL` at 10 s, error at 20 s): Electron's helpers outlive `bun run dev` and broke `rmSync` with `ENOTEMPTY`.
- Main-process stubs (folder picker, notifications, `shell.openExternal`) go through the Node inspector: `--inspect=0` (`--inspect <port>` for the dev script, which ignores 0), `Runtime.evaluate` with `includeCommandLineAPI: true` over `WebSocket`; the app has no test hook. Keep `--inspect` usable in test builds; disconnect it before stopping the group (it can hold the process).
- Playwright (Microsoft) without `_electron.launch()` (experimental; it runs the main script before returning, so startup output never reaches the test): tests spawn the app with `--remote-debugging-port=0`, attach output listeners at once, read the port from Chromium's `DevTools listening on` line and `chromium.connectOverCDP`. `attach` waits for the app's URL before reloading (the target starts as `about:blank`; a racing reload hangs). Console checks use `filter: 'all'` (the default drops what came before the last reload). Never disable the remote debugging port.
- Ratchet (COCKPIT-80, `.github/scripts/plane-sync/test/sleeps-ratchet.test.ts`): counts the pauses, `timeout:` options, `poll(` calls and `Date.now() +` deadlines in the test files against a `BASELINE`. It fails above (a new pause or deadline) and below (lower the baseline in the same change): a change that removes some lowers it. The sweep of what is left is COCKPIT-81.
- Pitfall: the router pushes the URL before it renders, so a test waits for the page's own content (the workspace page is a region named after the workspace), never the URL, and scopes its locators to that region. A closing Base UI menu stays in the DOM during its exit animation: find menus by accessible name, never an unnamed `getByRole('menu')`.
