# AGENTS.md — cockpit

**cockpit** is a provisional working name. In the desktop app: `Cockpit`, `com.cockpit.desktop`.

## What belongs in this file

Every session loads this file whole (Claude Code truncates at 150,000 characters), so it stays short; a test fails at 40,000.

- Keep: rules and conventions; technical choices with their verified facts (date, source), exit cost and trigger to revisit; pitfalls the code does not show.
- Leave out: feature behaviour (UI copy, messages, IPC lists, refusal texts, per-feature flows) and test case inventories. The code and the tests state them.
- A ticket adds a line only for a new package or app, a new rule, a new technical choice or a new pitfall.

## Rule #1: no over-engineering

Do not add any abstraction, package or app beyond what this file describes. When in doubt, do the simplest thing.

## Technical choices: long-term viability first

Choose a tool, library or framework on long-term viability: who maintains it (organization or single person), release activity, real adoption, compatibility with the stack, cost of leaving it. Setup speed and amount of configuration are no argument. Back the choice with verified facts.

## Working on this repo

For whoever develops Cockpit; the app imposes none of this on users' repositories:

- Everything in the repository is in English: code, identifiers, comments, docs, branches, commits, PRs.
- Never force push (lease included); a pushed branch catches up by merging `origin/main`.
- Read `git status`, then stage named files; never `git add -A`.
- A red CI is a bug: find its cause and fix it; rerun only for a cause outside the code.
- Non-blocking review notes go to a still-open ticket, never the shipped one.

## Product

A desktop app driving agent CLIs (Claude Code, Codex, OpenCode…) through node-pty, following Superset's projects / workspaces model. Differentiators: sessions outside any project; artifacts on storage you own; usage statistics.

Artifacts, stats, cloud backend, web app, mobile: none without an explicit request.

## Monorepo

- No business logic in `apps/`: it all lives in `packages/`, apps only wire things. No other app without an explicit request; `apps/cli` is COCKPIT-56's CLI and nothing else.
- Bun (package manager, workspaces, scripts) + Turborepo, TypeScript. Node 22+ for the tooling; the desktop app runs on Electron's Node (24 in Electron 44). A native module (`node-pty`) must be built for the runtime that loads it.
- By hand, no `create-turbo`: workspaces `apps/*`, `packages/*`, `.github/scripts/plane-sync`; `turbo.json` tasks `build`, `dev`, `test`, `typecheck`, `lint`; `tsconfig.base.json` extended by every package; one root `.oxlintrc.json`. `workspace:*` internal dependencies; packages consumed as TS source, no per-package build; `vitest`.
- `test` is never cached (its result depends on the machine: Electron binary, login shell; Turbo shares its cache across git worktrees), nor is `lint`, so a `.oxlintrc.json` change is never hidden.
- Linting is oxlint: a check-only `"lint": "oxlint"` script per workspace, no `--fix`, run by `bun run lint` through Turbo. Config: default plugins plus `react`, `correctness` as `error`, `routeTree.gen.ts` ignored (git-ignored paths skipped); no type-aware rules, other categories or formatting. Root `devDependency`.
  - Why (checked 2026-10-21): built by VoidZero (Evan You's company: Vite, Vitest, Rolldown), acquired by Cloudflare 2026-06-04, projects staying MIT; weekly releases; about 16.2 M downloads a week, 23,159 stars on `oxc-project/oxc`; own Rust parser, the only one of the three aligned with TypeScript 7, used by the repo. One npm publisher (`boshen`); code in a company organization.
  - Biome: community-run `biomejs` org, about $30k a year from sponsorship, 11.0 M downloads a week, 25,979 stars, own rule names and config (medium exit cost). ESLint (OpenJS Foundation, 96.1 M a week, 27,569 stars) + typescript-eslint (55.6 M a week, 16,435 stars): 8.72.0 declares `typescript >=4.8.4 <6.1.0` and imports TypeScript's JS API, which TS 7 lacks, so it needs TypeScript 6 alongside until TS 7.1 support lands.
  - Exit cost low: its rules are ports of ESLint, typescript-eslint, unicorn and react rules, same names. The lockfile pins CI's version, so only a deliberate `bun update` brings a new correctness rule failing CI.
  - Tests must not run the linter (CI runs `lint` and `test` in parallel).
- Layout: `apps/cli` (`cockpit` binary), `apps/desktop` (Electron), `packages/daemon` (owns every pty), `shell-env` (login-shell environment), `state` (JSON app state), `workspaces` (git worktrees), `harnesses` (agent CLIs), `launchers` (editors, terminal apps), `github` (pull requests through `gh`), `.github/scripts/plane-sync` (repo tooling run by a workflow, a workspace only so Turbo runs its tests in CI).

Commands: `bun install`; `bun run build|test|typecheck|lint` (turbo; `test` needs a desktop session); `bun turbo run build --filter=@cockpit/desktop && bun run --cwd apps/desktop vitest run test/<file>` (one desktop test file; `packaged.test.ts` and `launchd.test.ts` also need `package`); `bun run --filter @cockpit/desktop dev|package|test` (hot reload | `Cockpit.app` in `apps/desktop/release/` | dev, built and packaged app).

## Desktop app (`apps/desktop`)

- Stack: Electron 44, electron-vite, electron-builder, React 19, TanStack Router. electron-builder rather than Forge (no Bun support; its Vite plugin leaves `node_modules` out of the package, breaking node-pty). electron-vite has a single maintainer but is a thin layer over Vite: if abandoned, replace it with Vite and a dev script.
- UI: Tailwind CSS 4 (Tailwind Labs' team shrank in January 2026; releases continue), shadcn/ui on Base UI (`base-mira`; no runtime dependency, its CLI copies source we own; Base UI is MUI's, shadcn's default since July 2026), lucide, the system font. `cn` is 0.x since September 2026: if abandoned, `clsx` + `tailwind-merge`. `react-markdown` + `remark-gfm` (pull request bodies; remarkjs, MIT, 54.7 M downloads a week, 15,934 stars, checked 2026-11-05) drops raw HTML, so no `dangerouslySetInnerHTML` (marked, markdown-it: HTML strings to sanitize); exit cost: one component.
- `src/`: `main/` (window, `app://` protocol, IPC), `preload/` (`window.api` only), `shared/` (`Api` types), `renderer/`.
- Renderer boundary: no `electron` or Node import in the renderer; only `window.api`, typed by `Api` in `src/shared/api.ts`, reaches the main process. A future web app (TanStack Start) implements the same `Api` over HTTP; no such app or shared UI package until then. `Api` declares types like `ChangedFile` and `FileDiff` itself: importing them pulls Node types into the renderer's typecheck. A module a vitest test imports directly must not import through `@/` (one needing a type from there uses a cast).
- Security: `contextIsolation` and `sandbox` on, `nodeIntegration` off; a sandboxed preload cannot be an ES module: bundled as CommonJS (`index.cjs`). The renderer is served from `app://renderer`, never `file://`, with a CSP in `index.html`. New windows are denied (`https` goes to the system browser); navigation off the app origin is blocked, comparing origins rebuilt from protocol and host (`URL.origin` is `"null"` for `app:`, letting `app://other/` through). `about:blank` is not covered (Chromium commits it synchronously, no `will-navigate`; only the app's own code gets there). `navigateOnDragDrop` is off. Every privileged IPC handler ignores a sender frame that is not the app's page (`isFromApp`); an invoke rejects.
- Dependencies: what the bundles import goes in `devDependencies` (electron-vite bundles it); only unbundleable native modules (node-pty) go in `dependencies`, shipped and rebuilt by electron-builder.
- Styling: Tailwind utilities with the semantic tokens of `styles.css`, never raw colors or `dark:` color overrides. Tokens come from the Figma "Cockpit" file, page "Redesign — Linear direction", collections "Theme v2" and "Theme v2 / Light" (COCKPIT-65), in hex; radius scale 6, 8, 10, 12 px as fixed values, not `calc` of `--radius`. In the sidebar and the right bar no font weight above 400, Lucide stroke width 1.25. Diff and merged-state colors are tokens too (`--diff-added-foreground`, `--diff-removed-foreground`, `--diff-hunk`, `--status-merged`). Prefer a shadcn/ui component to custom markup: `bunx --bun shadcn add <name>` from `apps/desktop` (`components.json` is there; the `@/` alias in its `tsconfig.json` is for the CLI), move the packages it adds to `devDependencies`, add one only when a feature uses it.
- Right bar: the right column of a workspace page is a `div` with role `complementary` named "Right bar", never an `<aside>` (the left sidebar is the only one). Its state (`{ open, tab }`) is module-level. It reads git, watches the worktree and runs `gh` only while mounted: nothing runs while closed, a window focus included. Its buttons carry `transition-none`: shadcn's `transition-all` leaves a color mid-transition after a theme or tab change.
- Theme follows the system through `prefers-color-scheme` (driven by `nativeTheme`). Dark tokens live under `@media (prefers-color-scheme: dark)`, not `.dark` (move a CLI-added block).
- Window chrome: macOS hides the title bar (`trafficLightPosition: { x: 14, y: 16 }`); top strips drag the window (`app-drag`), interactive elements in them need `app-no-drag`; other platforms keep the native frame.
- The router reloads loaders `blocking` (`defaultStaleReloadMode` in `main.tsx`): with the default `background`, `await router.invalidate()` resolves with the data already shown, so a page opened after a change lacked it in the sidebar.
- A flow that navigates after an `await` claims it at the user's action (`claimNavigation(router.history)`), navigating only if its check holds (COCKPIT-86).
- `routeTree.gen.ts` is generated on `dev`/`build` and committed so `typecheck` works on a fresh checkout.
- Built assets use absolute paths: electron-vite forces `base: './'`, breaking nested routes on reload; a `post` plugin in `electron.vite.config.ts` sets `base: '/'`.
- Packaging: `package` builds the CLI, then an ad-hoc signed `Cockpit.app` with the CLI at `Contents/Resources/bin/cockpit` (`extraResources`). `signed-app.yml` (push to `main`) signs with Developer ID, hardened runtime, notarizes, runs the packaged and launchd suites on the result; `allow-jit` for helpers, CLI and node-pty, plus microphone, camera and Apple Events for the main app and daemon; installers, auto-update: later. A PR run never signs (`GITHUB_BASE_REF`); ad-hoc hardened needs `disable-library-validation`, so test builds stay non-hardened. electron-builder 26.16.1+ is needed (COCKPIT-97): earlier ones pass the `.p12` password to `set-key-partition-list -k` (`SecKeychainUnlock` error); chosen over a keychain built in the workflow. Since Electron 42 its binary downloads on the first `require('electron')`; `dev` runs `install-electron` first.
- Login-shell environment: an app started from the Finder or Dock gets launchd's minimal `PATH`, so the main process resolves the login shell's environment once per launch (`shellEnv`, `src/main/shell-env.ts`); every child process (git, `gh`, `open`, harness detection) spawns with `await shellEnv`; the daemon resolves its own once. The renderer gets only `PATH` (`window.api.getShellPath()`).
- Data locations: app data under `app.getPath('userData')`; worktrees, session folders and daemon files under `$COCKPIT_HOME`: `~/.cockpit` packaged, `~/.cockpit-dev/<folder>` unpackaged (its `userData` is `<that>/user-data`). `<folder>` is `devFolderName` of the worktree root: basename sanitized to `[A-Za-z0-9._-]` and cut to 20, `-`, 8 hex characters of the SHA-256 of its path, at most 29 bytes so `daemon-1-<build>.sock` fits macOS's 103-byte socket path limit. Worktrees and session folders are the user's work, not app data: the space in `Application Support` breaks some tools, and AppCleaner-type uninstallers wipe uncommitted work.
- Single instance: `app.requestSingleInstanceLock()` goes right after `app.setPath('userData', …)`, since Electron ties the lock to `userData`; a loser calls `app.exit(0)`.
- Workspace panes are rendered flat (one list keyed by pane id, placed by percent boxes; each pane's terminals stacked under its tab bar, unselected ones `invisible` at full size) so a split, close or tab switch remounts no view. Keys typed before `spawn` resolves are held and written once the id is set.
- Separators between panes are hand-written (one absolutely placed element per split, a `ratio` on each `Split`); react-resizable-panels rejected (checked 2026-11-02: 4.16.1, 29.8 M downloads a week, 5,446 stars, single npm maintainer): its nested Group/Panel elements would move a pane on a split or a close and remount its terminal. Exit cost: a component and three pure functions in `workspace-layout.ts`.
- The pane layout is not saved (COCKPIT-70): after a reload or restart a workspace's running sessions and shells return as the tabs of one pane, in creation order. A shell is spawned with its `workspace` so the daemon's list maps it back; one spawned without is not shown. The root loader does not await the restore: a daemon that does not answer (`SIGSTOP`) must not block the page.
- A workspace the composer sends (COCKPIT-89) is made by the daemon with no page (`workspaces:compose`): its terminal has no owner (one would let `adoptSession` attach it tab-less), `workspaces:settled` restores it as a tab, its `pty:exit` goes to every window.
- xterm.js pauses its renderer while its element is out of the page, and a fit or scroll handled meanwhile uses the old size: a re-attached terminal draws, then fits and restores its scroll. Base UI's modal menus make the page inert and return focus to their trigger, so a menu action that moves the keyboard gives it back to the terminal once the menu closes.
- Late spawn ack: a spawn resolving after its page navigated or was destroyed kills the terminal and throws `PageGoneError`; `pty:spawn` catches it and returns `-1`, so Electron logs no `Error occurred in handler` and a reload leaves no orphan shell. Only `commands` terminals (a teardown) end with their page: `did-navigate`, window destroyed, or `did-fail-load` except `ERR_ABORTED` (-3).
- Spawn defaults (`withSpawnDefaults`, `terminalEnv()` in `packages/daemon/src/environment.ts`): the login shell as a login shell (`-l`, default shell only), the home directory, the login environment minus what a session inherited, `TERM`, `COLORTERM`, `COCKPIT_SOCKET`, `COCKPIT_HOME` and the CLI's folder first on `PATH`; a request's own `env` replaces all.

## Daemon and terminals (`packages/daemon`)

Pure Node, importing neither `electron` nor `apps/` (a test checks it). Runtime dependencies: node-pty (native, shipped by electron-builder), `@xterm/headless` and `@xterm/addon-serialize` (bundled). `apps/desktop` only wires it: `src/main/daemon.ts` is the entry (`<Electron binary> <bundle> --cockpit-daemon <build>` with `ELECTRON_RUN_AS_NODE=1`; test teardown looks for that marker), `src/main/index.ts` connects and forwards `pty:*`. `@cockpit/daemon/cli` pulls neither node-pty nor xterm.

- It owns `state.json`, the only writer: `actions.ts` runs the `call` requests of the app and the CLI, each change reaching every connection as a `state` event. The app's `$COCKPIT_HOME/daemon-launch.json` lets `cockpit` start the daemon of that build, with launchd's base environment, not the shell's (`TMUX`, virtualenv, Claude Code).
- It owns every pty and outlives the app: quitting, reloading, updating, closing the window or `SIGKILL` of the app ends no shell or agent. It never idle-stops, no login service starts it (launchd is out of scope), the app starts it on demand.
- Files: flat in `$COCKPIT_HOME` as `daemon-<protocol>-<build>.{sock,token,pid,log}` (protocol `1`); `.sock` and `.token` mode `0600`; the token (32 random bytes, hex) is new at every start and written by rename; `.log` is kept. The build is the first 12 hex characters of the SHA-256 of the daemon bundle, `process.versions.electron` and node-pty's version, so an update changing none keeps the running daemon; `COCKPIT_TEST_DAEMON_BUILD`, when non-empty, replaces it in every build.
- `RunAsNode` fuse: needed by the daemon (on by default, untouched by `electron-builder.yml`); test builds also need `EnableNodeCliInspectArguments` and the remote debugging port; a fuse change must keep them. Why the app's Electron binary rather than a bundled Node (checked 2026-10-28): no second runtime to ship, sign, notarize and patch; node-pty's N-API prebuilds load under it. Exit cost: one spawn call. After an update only node-pty's `spawn-helper` is read again.
- Superseded rule: an app, or a ready daemon, connects to every other `daemon-1-*` socket (older builds first, so terminals list in creation order), saying `hello` with its build. A daemon hearing another build keeps its terminals, refuses its `spawn`s and writes (`WRONG_BUILD`) and exits once empty: new terminals run in the new build's daemon.
- Readiness (COCKPIT-83): the app starts the daemon with `stdio[3]` a pipe (`READY_FD`); the entry writes one line on it once `.token` and `.pid` are on disk, then closes it; `ensureDaemon` connects once, on that line, on the child's `exit` (a daemon of the build may still answer) or after 15 s (an alive daemon that never gets ready cannot notify). `connectDaemon` has no 401 retry: no client reaches a daemon before its token. Risk: the app and the CLI starting one build together can fail a start with a `401`; the next call recovers.
- Lazy restart: a dead daemon ends its terminals with `exitCode: null`; the next spawn or session start starts a new one. Terminal ids are the main process's counter, never reused across daemons. No crash-loop handling. A daemon that cannot start or does not answer in 5 s never stops the app: one stderr line, the window opens read-only, writes refused with the reason.
- Transport: HTTP over the Unix socket (`Upgrade: cockpit-1`, `Authorization: Bearer <token>` compared with `timingSafeEqual`; `401` with an empty body before anything else is read), then one JSON object per line. Output goes daemon, main, renderer; a `MessagePort` is impossible (the daemon is no Electron process of the app) and no measurement shows the main process as a bottleneck. Trigger to move: typing latency, or a saturated main process, with several terminals active. HTTP rather than JSON-RPC: no dependency either way, `curl --unix-socket` ships with macOS. Token next to the socket (`${COCKPIT_SOCKET%.sock}.token`), no `COCKPIT_TOKEN_FILE`. `POST /session-events` is the status endpoint of hooks and `cockpit setup`; `GET /terminals` and `POST /shutdown` never change (a shipped daemon cannot gain a route): the only calls to another protocol's daemon.
- Restoring: per terminal a headless xterm, serialized on `attach` (memory only); view and daemon both keep `SCROLLBACK` (1000 lines). Chunks and size changes share one per-terminal sequence number, so `attach` plus later events lose and duplicate nothing. A resize goes through the headless write queue and out as a `resize` event; a view takes a size only from it, in a write callback (chunks on their way were written for the old size, COCKPIT-91). A daemon without the `cockpit-resize-events` upgrade header sends none: its client reports the size at once.
- Ending a terminal: SIGHUP, then SIGKILL to its own process 1 s later if no exit was seen (timer `unref()`ed). Why: bash 3.2 (macOS `/bin/sh`) drops a SIGHUP arriving during startup and a script may trap `HUP`, so a lone SIGHUP could leave an unlisted process running, back as a tab after a reload (COCKPIT-64). The SIGKILL reaches neither children nor the group. Each per-terminal node-pty call is guarded (bad sizes, exit races).
- xterm.js (`@xterm/xterm` `^6.0.0`, `@xterm/addon-fit` `^0.11.0`, in the daemon `@xterm/headless` `^6.0.0` and `@xterm/addon-serialize` `^0.14.0`; stable rather than the 6.1 beta line VS Code tracks): `xtermjs/xterm.js` (organization), MIT, 21,285 stars, maintainer tyriar, a VS Code dependency; about 3.9 M / 3.4 M downloads a week (xterm / addon-fit); stable releases are rare (6.0.0 on 2025-12-22), betas continuous. Checked 2026-10-20. Exit cost: one component.
- node-pty: Microsoft (`microsoft/node-pty`, VS Code's terminal backend), about 2.5 M downloads a week, 2,050 stars (checked 2026-10-19). Pinned exactly to `1.2.0-beta.15`: 1.1.0's macOS `spawn-helper` lacks the execute bit (every spawn fails with `posix_spawnp failed`), 1.2.0 fixes it; move to 1.2.0 once published. Pinned in both `apps/desktop` (shipped by electron-builder) and `packages/daemon` (Bun's isolated linker resolves each workspace's own dependencies).
  - `npmRebuild: false`: node-pty is N-API, so its prebuilds load under Electron as they are. A rebuild compiled it in the shared Bun store (`node_modules/.bun/`), whose `build/` then shadowed the prebuilds for every later run: delete a rebuilt `build/`. `asarUnpack: node_modules/node-pty/**` keeps `pty.node` and `spawn-helper` runnable.

## State (`packages/state`)

The app state is one JSON file, `state.json`, in `userData`; the package does not import `electron`. A feature that stores a field adds it with a write API.

- Atomic, durable write: `state.json.tmp`, `fsync`, rename, then `fsync` of the folder so the rename survives a power loss (libuv's `fsyncSync` already does `F_FULLFSYNC` on macOS).
- Corrupted file: kept as `state.json.corrupt-<timestamp>` with its original bytes (hard link so `state.json` is never missing, else a copy; first free `-2`, `-3`… suffix, never overwriting), a fresh file written, a warning naming the backup. Newer version or unreadable file: touch nothing, no window, stderr message, exit 1.
- Git is the source of truth for worktrees: the state never stores what `git worktree list` can tell. Exception: the `mainWorkspace` mark.
- Why JSON rather than SQLite (checked 2026-10-20): a few small records written by one process; JSON has nothing to maintain, and leaving costs one migration driven by `version`. `node:sqlite` in Node 24.22.0 (Electron 44.9.x) is "Stability: 1.2 - Release candidate": built in but not Stable, and it moves with Electron's Node. `better-sqlite3` 13.0.3 (2026-08-05): single npm maintainer (joshuawise), 7.2 M downloads a week, 7,522 stars, N-API prebuilds since 13.0.0 but still native.

## Workspaces (`packages/workspaces`)

Pure Node, no `electron` import (a test checks it). Functions take an optional `env` for git.

- A package called by the main process, not a CLI (checked 2026-10-19: Superset, Orca, Emdash, Vibe Kanban, Claude Squad: none calls its own CLI). Errors are typed (`WorkspaceError`, a `code` surviving IPC) from pre-checks and exit codes, never git's localized messages.
- `execFile('git', …)` on the user's git, never a shell, no git library: the git manual guarantees a stable `git worktree list --porcelain`. simple-git: no worktree API, one de facto maintainer; dugite: ships its own git binary (to sign); isomorphic-git: no worktrees; nodegit: last stable 2020. git 2.36+ (`worktree list --porcelain -z`), checked at runtime (`GIT_MISSING`, `GIT_TOO_OLD`).
- Layout `<root>/<project>-<hash>/<branch>`, `<hash>` the first 8 hex characters of the main working tree path's SHA-256 (stateless; no same-name collisions). A workspace is a linked worktree; the main working tree is the project, listed only as its main workspace. Calls per repository are serialized. `createWorktree` is all-or-nothing, its rollback (`git worktree remove --force`, `git branch -D`) removes only its own.
- Main workspace (COCKPIT-71): the project's own folder, one per project, identified by its path; `mainWorkspace` in `state.json` is the whole record. `toProject` and `findWorkspace` let it through, `workspaces:compose` takes a `null` base: no parallel path. No `setup`, `teardown` or `cockpitName`; a moved project's running terminals stay under the old path.
- Base: recorded as `branch.<name>.cockpitBase` in git config before `git worktree add` (unset in the rollback); an unresolvable base falls back to the default base, then `NO_BASE`. Untracked files reach `git diff` via an index copy (`GIT_INDEX_FILE`). Reads never write under the gitdir (its watcher would loop): `git --no-optional-locks status --porcelain`, index copies.
- Readable name: `branch.<branch>.cockpitName` in git config (git is the source of truth, not `state.json`), given by `listWorktrees` as `Worktree.name`. `nameWorkspace` renames the branch with `git branch -m`, carrying `cockpitBase` and the branch's other settings, only when the branch is not pushed (its upstream is not a branch of its own name; one made from a remote base tracks that base, which does not count). The folder stays.
- `watchWorktree`: recursive `fs.watch` (FSEvents, macOS only), 200 ms debounce, git metadata too (commits, pushes, fetches in a terminal). FSEvents reports nothing from before its stream starts, so the start touches the mtime of every watched folder until each reports (2 s max). A touch in flight reports later: `isFolderTouch` (`src/changes.ts`) ignores, at any time, a `change` event named like the watched folder when no file has that name (a folder of that name counts); waiting for them to die down raced them. The format is libuv's, undocumented: an Electron update changing it brings spurious refreshes back (none lost) and fails `changes.test.ts` AC7. A top-level file named like the folder keeps one start-up refresh.
- Every git call has a 256 MiB `maxBuffer` (`git()` in `src/git.ts`; Node's 1 MiB default failed a long `status` or chatty hook). `fileDiff`'s 1 MiB limit is its explicit `maxBuffer`, winning over the default.
- In a stopped rebase HEAD is detached: the branch (and its base) is read from `rebase-merge/head-name` or `rebase-apply/head-name`, as `git-prompt.sh`; nothing is written.
- Removal: a dirty worktree is refused (`DIRTY_WORKTREE`) unless `force`; a branch goes by `git branch -d`, unmerged (squash-merged too) kept (`BRANCH_NOT_MERGED`) unless `forceBranch` names it (`-D`); only the delete dialog sends them. Push is `git push --set-upstream origin <branch>` with `GIT_TERMINAL_PROMPT=0`, never `--force`, `--force-with-lease` or a `+refspec`.
- New repositories: `initRepository` makes an empty commit (a worktree and `listBranches` need one) and, with no identity (`git var` in the new repository), removes `.git`. A failed or cancelled clone is removed once git exits: git keeps its folder when killed or failing at checkout (2.50.1, 2026-11-05).
- Config (`readWorkspaceConfig`): `<main working tree>/.cockpit/config.json`, `{ "setup": string[], "teardown": string[] }`, read from the main working tree only (a worktree's own is ignored); any other shape or key is `INVALID_CONFIG`.

## Harnesses (`packages/harnesses`)

Pure Node, no `electron` import (a test checks it), no runtime dependency, deep-frozen catalogue.

- Only verified harnesses are listed: official docs, the CLI's own `--help` or output, or official source at a release tag, each fact sourced in a comment in `src/catalogue.ts` or `status.ts`. Checked 2026-10-20 against Claude Code 2.1.304, Codex 0.163.0, OpenCode 2.0.31 (status: 2026-10-25, 2.1.310). They release weekly and tests use stubs, so nothing catches a renamed flag or a changed format: re-check at every entry update. Codex's session path comes from its source; OpenCode's from `opencode debug paths` (docs: 1.x).
- Left out: Cursor CLI (session storage undocumented, closed source); Kimi (legacy `kimi-cli` archived, its `kimi` runs no agent; successor Kimi Code CLI takes no initial prompt interactively); Mistral Vibe (by decision: 3.0, a Rust rewrite, shipped 2026-10-19; session layout only in the source).
- Detection runs in the main process once per launch, started by the first render of the New workspace page (never at startup); `sessions.harnesses({ again: true })` reruns it and replaces the shared result. Detection walks `env.PATH` and runs `<path> --version` with the given `env` in its own process group, all in parallel, never rejecting; on timeout it `SIGKILL`s the group and settles without waiting for `close` (a child can hold stdout).
- Prompt-derived title (`promptTitle` in `src/catalogue.ts`, formats and sources in comments): the terminal title (OSC 0/2) a harness sets from the user's first prompt names a workspace; idle and unrelated titles give `null`. Titles count only between the private OSC 6973 markers `cockpit setup` writes in the stream, `agent-started` right before the agent spawns and `agent-exited` right after it ends (`AGENT_MARKER_OSC`, `packages/daemon/src/protocol.ts`): the daemon's headless parser reads them in order with the output: a title from the setup or the login shell is never the agent's, whatever the timing. Never decide that by a delay or the order of two channels (the status reports travel apart and hold nothing back); register the pending rename before the spawn. Formats were read in the CLIs' sources and nothing catches a change (it only means no rename).
- Status reporting (`statusLaunch`): harnesses run `cockpit status <event>` (`working`, `waiting`, `finished`), set up through argv and environment only (Claude Code `--settings`, Codex `-c hooks=…`, an OpenCode plugin file), never in the user's repo or global config. Codex runs a hook only when trusted, so the `-c` carries a `trusted_hash` from a formula taken from Codex's source, not its docs: a release changing it shows "Hooks need review" with no dot. Out of scope: overriding `disableAllHooks`, `features.hooks = false` or an admin policy; terminal-output heuristics.
- Interrupt (COCKPIT-50): Claude Code fires no hook on an Esc and its transcript shows nothing for one before any output, so the daemon reads `turnTitles`. Undocumented title, checked 2026-11-07 (2.1.319).
- Conversation id (COCKPIT-30): reported at the prompt (second `UserPromptSubmit` hook, Codex key `:0:1`; OpenCode's plugin), so a stored id names an existing conversation; the hook's field names stay in `packages/harnesses` (a test checks the daemon, state and desktop sources).

## Launchers, GitHub and shell-env

Pure Node, no `electron` import, no runtime dependency. `launchers` and `github` are packages of their own (`workspaces` is git).

- Launchers: detection only stats `<bundle>.app` in the applications folders (no `open`, Launch Services or Spotlight query, cache or editor CLIs). Runs use `open -a <absolute bundle path>`, since `open -a <name>` may pick another copy than the one detected; `execFile('open')`, never a shell. Sources checked 2026-10-25, each a comment in `src/catalogue.ts`; Warp rests on its docs only (closed source): drop it if a release breaks it.
- GitHub: `gh` through `execFile` with `GH_PROMPT_DISABLED=1`; ENOENT is `GH_MISSING`, exit 4 `GH_UNAUTHENTICATED`. An unknown check value is never passing. Risk: check and review values are GraphQL enums; a new one reads as unknown. Sidebar icons: one `gh api graphql` per expanded project, on show, focus, merge or create; never a timer.

## CLI (`apps/cli`)

The `cockpit` command line (COCKPIT-56). Its logic is `runCli` in `packages/daemon/src/cli.ts` (`@cockpit/daemon/cli`; `setup`/`teardown` in `src/setup.ts`); `apps/cli/src/main.ts` only passes `process`; `bun build --compile` makes `apps/cli/dist/cockpit`, it ships at `Contents/Resources/bin/cockpit` packaged; the daemon gets that absolute path (`COCKPIT_CLI`) and passes it to `statusLaunch`, so older sessions' hooks run the new binary against the old daemon.

- `cockpit status` and `cockpit session-id <harness>` (stdin through the adapter) always exit 0, write nothing and give up on the daemon after 2 s (stdin is unbounded: the harness closes it or kills the hook): a failing hook shows an error in Claude Code and Codex, and some hooks' stdout reaches the model. Other usage errors exit 2.
- `setup`/`teardown` run each repository command in its own `/bin/sh -c`. The CLI ignores `SIGINT` and `SIGQUIT`: a Ctrl+C reaching its process group ends the child, not the CLI.
- `terminal send` pastes (bracketed if asked); `agent wait --after <n>` skips a turn.
- Ending (COCKPIT-64): the daemon's SIGHUP then SIGKILL hit only the CLI's pid, and the kernel's hangup reaches only the foreground group, which an interactive login shell takes, orphaning the agent or shell. So the CLI catches SIGHUP and SIGTERM, synchronously signals every process under it (`ps -axo pid=,ppid=`, whatever its group), waits up to 300 ms, SIGKILLs the rest and exits 129 or 143, before the daemon's SIGKILL. Limits: daemonized processes; macOS `ps`.
- Why a Bun compiled binary (checked 2026-10-28, macOS arm64, 30 runs, median / p90): the former `curl` line via `/bin/sh -c` 11.2 / 11.9 ms; Bun 1.4.3 compiled 15.0 / 16.1 ms; Node 24 35.1 / 37.0 ms; Electron 44 with `ELECTRON_RUN_AS_NODE=1` 50.7 / 52.7 ms. `oven-sh/bun`: organization repository (Oven, acquired by Anthropic 2025-12-02, MIT, public development), 96,449 stars, 5.3 M npm downloads a week; it cross-compiles to Linux and Windows (COCKPIT-58, COCKPIT-59). Exit cost low: the logic is plain Node in `packages/daemon`; another build (Node SEA, Rust, Go) replaces only the compile step. Risk: +68 MB.
- Pinned Bun: the compiler is the root `packageManager` version (`bun@1.4.2`), through an exact `bun` devDependency of `apps/cli` and `bun.lock`, so updating Bun on a machine or in CI never changes the shipped CLI. `scripts/check-bun.ts` fails the build on a mismatch; change `packageManager` and the devDependency together.

## CI and Plane sync

- CI (`ci.yml`): `changes` (`ci-scope.sh`) gates the rest. A push to `main`, or a PR touching `bun.lock`, the root `package.json`, `turbo.json`, `tsconfig.base.json`, `.oxlintrc.json`, `ci.yml`, `.github/actions/**` or the script, runs everything, else `--affected` (turbo misses those files). Linux: `lint`, `typecheck`, `repo-checks` (plane-sync tests read other workspaces: every PR). macOS: `packages`, `desktop` (3 vitest `--shard`s, each packaging the app). `check` (`always()`, needs all) is what the `main` ruleset requires: PR, up to date, no force push or deletion, administrators included.
- Plane sync (`plane-sync.yml`, `.github/scripts/plane-sync`): a merged PR to `main` moves its ticket (`COCKPIT-N` of the title or branch) to Done and unblocks the tickets it blocks; `PLANE_API_KEY` is needed only with a ticket id; fork PRs get no secret. Title, branch and secret reach the script through `env`, never a `run:` expression. Plane REST v1: v2 has no relations endpoint (checked 2026-10-21).

## Tests

- No version ships with a risk of crashing at runtime: `build` and `typecheck` are not enough. `test` (vitest + Playwright, `apps/desktop/test/`) launches the app the four ways it runs: the `dev` script, the built app, the packaged `Cockpit.app`, and the packaged app with launchd's minimal environment. Each must render, keep Node out of the renderer, log no error and keep running.
- One test file per feature area, never a catch-all; split a file past about 1,500 lines. Feature files launch only the built app; what needs the dev server or the package sits in `dev-server`, `packaged` and `launchd.test.ts`. Shared helpers: `test/support/`. Iterate on one file, run the full suite once at the end.
- Split rule: a feature's full block runs once, in the built app; each other mode runs one smoke path per feature, through its IPC end to end. The launchd mode keeps only paths that spawn git or a shell. An assertion runs in every mode only when what it checks differs between modes; test at the lowest level that can observe the behaviour (a package's vitest before Playwright).
- Tests never run a real agent CLI, `gh`, `open` or notification: `#!/bin/sh` stubs on a fake login shell's `PATH`, and `SHELL=/bin/sh` except in the launchd mode. Daemon on real sockets (short temp folders) and node-pty; workspaces on real git; harnesses, launchers, github against stubs; state, shell-env on temp folders and fake shells; `apps/cli` as the compiled binary.
- Test launches stay unnoticed. Read by the main process before `ready`, packaged app included: `COCKPIT_TEST_BACKGROUND=1` (accessory policy: no Dock icon, never frontmost; windows never shown, rendering as if visible), `COCKPIT_USER_DATA_DIR`, `COCKPIT_HOME` (a short `<data folder>/h`), `COCKPIT_TEST_APPLICATIONS_DIR`, `COCKPIT_TEST_DAEMON_BUILD`; a fresh `mkdtemp` folder per launch. The visible-window launch runs only in CI (the runner's `CI` reaches vitest directly); never set `CI` locally.
- Guard for the default folders: a launch leaving `COCKPIT_USER_DATA_DIR` unset or empty uses the app's default: a regression writes into the real `~/Library/Application Support/@cockpit/desktop`, and `HOME=<tmp>` alone does not prevent it (Electron's `appData` ignores `HOME` on macOS). So `launchEnv` in `test/launch.ts` throws unless such a launch has a `HOME` inside the run root, and sets `CFFIXED_USER_HOME=<HOME>`, moving `~/Library`.
- Run root and cleanup: a global setup (`test/global-teardown.ts`) makes one `ck-` folder per run in `/private/tmp` (`COCKPIT_TEST_RUN_ROOT`), folder prefixes at most 3 characters so socket paths fit. The daemon outlives the app: `close()` kills the home's daemons by `.pid`, the global teardown every daemon under the root with `--cockpit-daemon` on its command line (other runs' are left alone). `stopGroup` sends `SIGKILL` to the group and waits for the child's `close`, firing once every process holding its stdio is gone (no `SIGTERM` first, no timer): Electron's helpers outlive `bun run dev` and broke `rmSync` with `ENOTEMPTY`.
- Main-process stubs (folder picker, notifications, `shell.openExternal`) go through the Node inspector: `--inspect=0` (`--inspect <port>` for the dev script, which ignores 0), `Runtime.evaluate` with `includeCommandLineAPI: true` over `WebSocket`; the app has no test hook. Keep `--inspect` usable in test builds; disconnect it before stopping the group (it can hold the process).
- Playwright (Microsoft) without `_electron.launch()` (experimental; it runs the main script before returning, so startup output never reaches the test): tests spawn the app with `--remote-debugging-port=0`, attach output listeners at once, read the port from Chromium's `DevTools listening on` line and `chromium.connectOverCDP`. `attach` waits for the app's URL before reloading (the target starts as `about:blank`; a racing reload hangs). Console checks use `filter: 'all'` (the default drops what came before the last reload). Never disable the remote debugging port.
- Ratchet (COCKPIT-80, COCKPIT-81, `.github/scripts/plane-sync/test/sleeps-ratchet.test.ts`): counts per test file the pauses, `timeout:` options, polls and `Date.now() +` deadlines against a per-file `BASELINE` (non-zero entries only). A file above its entry fails (a new wait), below fails too (lower the entry in the same change). A re-check loop whose source cannot notify ends with `// legitimate poll: <reason>`, is counted nowhere and must be listed in the ratchet's `ALLOWED` (file, line, reason). Tests wait on events: `launch.ts` has `fifo()`, `heldProcess()`, `gonePipe()` and `untilDom()`, and `attach` sets the one default action timeout (`UI_TIMEOUT`), so no call passes `timeout:`. A criterion's time bound ("within 5 s") is a measure taken after the event wait (`startClock()` in `launch.ts`), never a wait's timeout.
- Pitfall: the router pushes the URL before it renders, so a test waits for the page's own content (the workspace page is a region named after the workspace), never the URL, and scopes its locators to that region. A closing Base UI menu stays in the DOM during its exit animation: find menus by accessible name, never an unnamed `getByRole('menu')`.
- Pitfall: never run the suite with the Mac asleep. Node's clock counts sleep: guards armed before fire at the wake (COCKPIT-81).
