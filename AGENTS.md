# AGENTS.md — cockpit

**cockpit** is a provisional working name. It appears in the desktop app (`Cockpit`, `com.cockpit.desktop`).

## Rule #1: no over-engineering

Do not add any abstraction, package or app beyond what this file describes. When in doubt, do the simplest thing.

## Technical choices: long-term viability first

When choosing a tool, library or framework, the criterion is long-term viability: who maintains it (an organization or a single person), release activity, real adoption, compatibility with the rest of the stack, and the cost of leaving it. Setup speed and amount of configuration are not arguments. Back the choice with verified facts.

## Language

Everything in this repository is written in English: code, identifiers, comments, documentation, branch names, commit messages, and pull request titles and descriptions.

## Product

A desktop application that drives agent CLIs (Claude Code, Codex, OpenCode, Kimi, Mistral, Cursor CLI…) through node-pty, following Superset's projects / workspaces model.

Differentiators:
- sessions outside any project (multi-agent exploration without a repository);
- artifacts on storage you own;
- usage statistics.

The repository is built in steps. So far, the parts in scope are the **desktop app shell** (`apps/desktop`): a window, a router, a typed bridge to the main process, and the UI foundation (styling, light and dark themes, sidebar layout); and the **daemon** (`packages/daemon`), the background process that owns every pty (node-pty, with a headless terminal per pty to replay its screen) and exposes them as `window.api.pty`, with the client that finds or starts it and the endpoint processes started by the app reach it through; the **login-shell environment** (`packages/shell-env`), which the main process resolves at startup for the child processes it will spawn; the **state store** (`packages/state`), which keeps the app state in a JSON file; the **workspaces package** (`packages/workspaces`), which creates, lists and removes git worktrees (`listBranches` feeds the base choice) and reads the repository's setup and teardown commands (`readWorkspaceConfig`) and turns them into a `/bin/sh` invocation (`commandsInvocation`); the **harnesses package** (`packages/harnesses`), which catalogues the agent CLIs and detects which are installed; the **launchers package** (`packages/launchers`), which catalogues the editors and terminal apps and opens a worktree in one or reveals it in the Finder; and the **github package** (`packages/github`), which reads and creates a branch's pull request through the GitHub CLI. The product UI is the **terminal page** (`/terminal`): xterm.js connected to shells through `window.api.pty`, in tabs and splits that keep running when the user goes to another page, reloads the page or quits the app, and the **projects** section of the sidebar: add, list and remove git repositories through `window.api.projects`, and create, list and delete their workspaces (git worktrees) through `window.api.workspaces`, running the repository's setup commands after a workspace is created and its teardown commands before one is deleted; and the **sessions** section of the sidebar: start an agent CLI in a folder of its own, outside any project, or in a workspace's worktree, through `window.api.sessions`; the **changes sidebar** of a workspace's session page: the files changed against the workspace's base and the diff of each, through `window.api.workspaces`; and, in a workspace's "…" menu, opening its worktree in an editor or a terminal app, or revealing it in the Finder, through `window.api.workspaces`; the **ship section** of the changes sidebar: commit, push, and the branch's pull request with its CI status, through `window.api.workspaces`.

Artifacts, stats, cloud backend, web app, mobile: create none of these without an explicit request. The daemon is the background process of `packages/daemon`, not an app of its own.

## Monorepo

- **No business logic in `apps/`.** Everything lives in `packages/`; apps only wire things together.
- **Bun** (package manager, workspaces, script runner) + **Turborepo**, TypeScript.
- Runtime: **Node 22+** for the tooling, the oldest supported LTS line; the desktop app runs on the Node bundled with Electron (24 in Electron 44). A native module (`node-pty`) must be built for the runtime that loads it.
- Set up by hand, without the `create-turbo` template:
  - root `package.json`: `apps/*`, `packages/*` and `.github/scripts/plane-sync` workspaces, scripts that delegate to Turbo;
  - `turbo.json`: `build`, `dev`, `test`, `typecheck`, `lint` tasks. `test` is never cached: its result depends on the machine (the Electron binary, the user's login shell), not only on the files, and Turbo shares its local cache across git worktrees. `lint` is never cached either (`"cache": false`), so a change to `.oxlintrc.json` is never hidden by a cached result;
  - `tsconfig.base.json`, extended by every package;
  - `.oxlintrc.json`: the one oxlint config, shared by every workspace (no per-package config).
- Internal dependencies declared as `"workspace:*"`.
- **Linting: oxlint.** Every workspace has a check-only `"lint": "oxlint"` script, without `--fix` (no fix script), and `bun run lint` runs them all through Turbo, uncached. The root `.oxlintrc.json` enables oxlint's default plugins plus `react`, the `correctness` category as `error`, and ignores the generated `routeTree.gen.ts`; oxlint also skips git-ignored paths. Type-aware rules, other categories and formatting are not set up. `oxlint` is a root `devDependency`, like `typescript`.
  - Why oxlint (facts checked on 2026-10-21 against npm, the GitHub API and the official sites): it is built by VoidZero (Evan You's company: Vite, Vitest, Rolldown), which Cloudflare acquired on 2026-06-04 with the projects staying MIT; releases are weekly (1.0.0 on 2025-06-10, 1.89.0 on 2026-10-19); about 16.2 million downloads a week and 23,159 stars on `oxc-project/oxc`; it has its own Rust parser and is the only one of the three aligned with TypeScript 7, which the repo uses. Its npm publisher is a single account (`boshen`), while the code lives in an organization owned by a company.
  - Against Biome (`biomejs` org, community-run, about $30k a year from sponsorship, 11.0 million downloads a week, 25,979 stars, own rule names and config format, so a medium exit cost) and ESLint with typescript-eslint (ESLint: OpenJS Foundation, 96.1 million downloads a week, 27,569 stars; typescript-eslint: 55.6 million downloads a week, 16,435 stars): typescript-eslint 8.72.0 declares `typescript >=4.8.4 <6.1.0` and imports TypeScript's JS API, which TypeScript 7 does not ship, so linting this repo would need TypeScript 6 installed side by side until TS 7.1 support lands.
  - Exit cost: low. oxlint's rules are ports of ESLint, typescript-eslint, unicorn and react rules under the same names, and its config is shaped like ESLint's.
  - oxlint ships weekly and `^1` lets a new correctness rule fail CI after a lockfile update; the lockfile pins the version CI uses, so that only happens with a deliberate `bun update`.

- **Internal packages consumed as TS source**, with no separate per-package build.
- **Tests** with `vitest`.

## Desktop app (`apps/desktop`)

- **Stack**: Electron 44, electron-vite (dev server and build), electron-builder (packaging), React 19, TanStack Router with file-based routes.
  - electron-builder rather than Electron Forge: Forge does not support Bun, and its Vite plugin leaves `node_modules` out of the package, which breaks native modules such as node-pty.
  - electron-vite has a single maintainer. It is a thin layer over Vite: if it is abandoned, replace it with Vite and a dev script. Packaging does not depend on it.
- **UI**: Tailwind CSS 4, shadcn/ui components on Base UI (`base-mira` style, made for dense interfaces), lucide icons, the system font.
  - Tailwind is a build-time tool maintained by Tailwind Labs. Its team shrank in January 2026 but releases continue; a frozen version keeps working.
  - shadcn/ui is not a runtime dependency: its CLI copies component source into the repo, which we own and edit. Base UI is maintained by the MUI company and is shadcn's default since July 2026.
  - Components import `cn`, shadcn's class merger, still young (0.x since September 2026). If it is abandoned, replace it with `clsx` + `tailwind-merge`, which have the same API.

```
src/
  main/       # main process: window, `app://` protocol, IPC handlers
  preload/    # exposes `window.api`, nothing else
  shared/     # the `Api` contract, types only
  renderer/   # React app
    routes/         # file-based routes; `__root.tsx` holds the sidebar layout
    components/     # app components
      ui/           # shadcn/ui components, added by the CLI
    styles.css      # Tailwind entry and theme tokens
```

- **Renderer boundary.** The renderer never imports `electron` or Node modules. It reaches the main process only through `window.api`, typed by `Api` in `src/shared/api.ts`. A future web app (TanStack Start) implements the same `Api` over HTTP and reuses the routes.
- **No web app or shared UI package** until a web target exists. When it does, move the renderer into a package consumed by both apps.
- **Security**:
  - `contextIsolation` and `sandbox` on, `nodeIntegration` off. A sandboxed preload cannot be an ES module, so it is bundled as CommonJS (`index.cjs`).
  - The built renderer is served from the `app://renderer` protocol, never `file://`, with a CSP in `index.html`. The router therefore uses real URLs, as on the web.
  - New windows are denied (`https` links open in the system browser), and navigation away from the app origin is blocked. The guard compares origins rebuilt from protocol and host (`URL.origin` is `"null"` for `app:`, so it would let `app://other/` through). `about:blank` is not covered: Chromium commits it synchronously, with no `will-navigate`, and only the app's own code can navigate there. `navigateOnDragDrop` is off: a dropped file does not navigate the window, and drops do nothing until a feature handles them.
  - Every privileged IPC handler in the main process (`pty:*`, `daemon:*`, `projects:*`, `workspaces:*`, `sessions:*`, `get-shell-path`) ignores a message whose sender frame is not the app's own page (`app://renderer`, or the dev server origin in dev); an invoke handler rejects.
- **Dependencies**: everything the bundles import goes in `devDependencies`, and electron-vite bundles it. Only modules that cannot be bundled (native modules such as node-pty) go in `dependencies`, so electron-builder ships them and rebuilds them for Electron.
- **Styling**:
  - Tailwind utilities with the semantic tokens defined in `styles.css` (`bg-background`, `text-muted-foreground`, `bg-sidebar`…), never raw colors or `dark:` color overrides.
  - Use a shadcn/ui component before writing custom markup. Add one with `bunx --bun shadcn add <name>` from `apps/desktop` (`components.json` lives there, and `tsconfig.json` carries the `@/` alias only for the CLI). The CLI adds packages to `dependencies`: move them to `devDependencies`.
  - Add a component when a feature uses it, not ahead of time.
- **Theme**: follows the system through `prefers-color-scheme`, which Electron drives from `nativeTheme`. Dark tokens live under `@media (prefers-color-scheme: dark)`, not a `.dark` class; if the shadcn CLI adds a `.dark` block, move its variables there. A theme setting, when requested, sets `nativeTheme.themeSource` in the main process, which switches the page and the native window chrome together.
- **Window chrome**: on macOS the title bar is hidden and the window controls sit in the sidebar's top strip. The top strips of the sidebar and of each page header drag the window (`app-drag`); an interactive element inside one needs `app-no-drag`. Other platforms keep the native frame.
- **Generated route tree**: `src/renderer/routeTree.gen.ts` is generated by the router plugin on `dev` and `build`, and committed so `typecheck` works on a fresh checkout.
- **Output**: electron-vite builds to `dist/` (the Turbo `build` output), electron-builder packages to `release/`.
- **Packaging**: `package` builds an ad-hoc signed `Cockpit.app` for the current platform. Developer ID signing, notarization, installers and auto-update come later, on request.
- **Electron binary**: since Electron 42 the `electron` package no longer downloads its binary on install; it does so the first time `require('electron')` runs. electron-vite reads the binary path without triggering that download, so `dev` runs `install-electron` first (a no-op once the binary is there).
- **Login-shell environment**: an app started from the Finder or the Dock gets launchd's minimal `PATH`, so the main process resolves the environment of the user's login shell once per launch (`resolveShellEnv` from `@cockpit/shell-env`, exported as `shellEnv` by `src/main/shell-env.ts`). Anything that spawns a child process (git, harness detection) must spawn with `await shellEnv`. A pty's `env` defaults to it (see Spawn defaults), and the shell it runs is the one that environment's `SHELL` names. The renderer only gets `PATH`, through `window.api.getShellPath()`.
- **Terminals**: node-pty runs in the **daemon** (COCKPIT-55), a background process of its own that the app starts on demand and that outlives it: quitting, reloading or updating the app, closing its window, or killing it with `SIGKILL` ends no shell and no agent. Only the process exiting, the daemon dying (a crash, `kill`) or a reboot ends one. The daemon never stops by itself (no idle timeout) and no login service starts it (launchd is out of scope).
  - `packages/daemon` holds the logic and imports neither `electron` nor `apps/`: `runDaemon({ home, build })` (the server, in `src/server.ts`) owns the node-pty terminals of `src/terminals.ts`, `ensureDaemon({ home, build, spawn })` and `connectDaemon(socketPath)` (`src/client.ts`) give the main process a `DaemonClient`, `daemonFiles` and `listDaemonFiles` (`src/paths.ts`) name and find a daemon's files, `statusCommand` (`src/status.ts`) is the hooks' shell line. `apps/desktop` only wires it: `src/main/daemon.ts` is the daemon entry (bundled through electron-vite's `?modulePath` import, run as `<Electron binary> <bundle> --cockpit-daemon <build>` with `ELECTRON_RUN_AS_NODE=1` and `COCKPIT_HOME` in its environment; the marker is what a test teardown looks for on a pid's command line), `src/main/index.ts` connects to the daemons, maps the renderer's pty ids to (daemon, terminal) and forwards the `pty:*` IPC, and the preload exposes `window.api.pty` and `window.api.daemon`. The only runtime dependencies of the package are node-pty (native, shipped by electron-builder) and `@xterm/headless` and `@xterm/addon-serialize` (bundled into the daemon).
  - **Daemon files and build**: a daemon's files sit flat in `$COCKPIT_HOME` (macOS caps a socket path at 103 bytes) under `daemon-<protocol>-<build>`: `.sock` (mode `0600`), `.token` (mode `0600`, 64 lowercase hex characters from 32 random bytes, new at every start, written to a temp file and renamed), `.pid` and `.log` (the daemon's stdout and stderr, kept after it exits; the other three are removed when it exits). The protocol is `1`. The **build** is the first 12 hex characters of the SHA-256 of the daemon bundle's bytes, `process.versions.electron` and node-pty's version, so an app update that changes none of them keeps the daemon it left running; `COCKPIT_TEST_DAEMON_BUILD`, when non-empty, replaces it (honoured in every build, so a test plays an update). The main process computes it, spawns the daemon detached into its own session (`process.execPath`, `ELECTRON_RUN_AS_NODE=1`, stdio to the log) before it opens its window, and a later launch on the same home finds the socket and reuses the daemon.
  - **The daemon depends on Electron's `RunAsNode` fuse** (on by default, untouched by `electron-builder.yml`): without it the app's binary cannot run the daemon bundle. Any later fuse hardening (Developer ID signing, notarization) must keep `RunAsNode` on, as it must keep `EnableNodeCliInspectArguments` for `--inspect` in test builds. Why the app's Electron binary rather than a bundled Node (facts checked on 2026-10-28): no second runtime to ship, sign, notarize and patch; node-pty's N-API prebuilds already load under it; the fuse governs it; VS Code's `code` CLI runs the same way. Exit cost: one spawn call. Once started, the daemon reads nothing from the app bundle (one bundle, node-pty loaded at start); after an update only node-pty's `spawn-helper` is read again, at a spawn.
  - **Updates: the superseded rule.** An app connects to every `daemon-1-*` socket of its home (the older builds first, so the terminals list in creation order) and says `hello` with its own build. A daemon that hears a build other than its own is **superseded**: it keeps its terminals, refuses any `spawn` from a client of another build (`this background service belongs to another build of Cockpit`, nothing spawned), and exits, removing `.sock`, `.token` and `.pid`, as soon as it holds none (at once when it holds none when the hello arrives). New terminals therefore run in the daemon of the new build, and the old agents' hooks still reach the old daemon through their own `COCKPIT_SOCKET`. Daemons of another protocol are left alone and not shown. No update flow, auto-update or "restart the background service" exists yet.
  - **The daemon restarts lazily.** `ensureOwnDaemon()` connects to this app's daemon, or spawns one and waits for it to listen; spawns issued together share the start. If the daemon dies (`SIGKILL`, a crash), its client reports the close: every terminal it held ends with `exitCode: null` (`[Process ended]`, a session's entry shows "Ended"), and the next `spawn` or session start starts a new daemon. Terminal ids are the renderer's own (a counter of the main process), so an id of a dead daemon is never reused: `write`, `resize` and `kill` on it do nothing to a new terminal. No crash-loop handling.
  - **A daemon that cannot start** (`COCKPIT_HOME` a regular file, `daemon-1-<build>.sock` a folder, a live socket of another process…) never stops the app: `ensureDaemon` rejects with the last line of the log (the daemon prints its error message there before it exits 1; a failure to open the log names its path), the main process writes one line to stderr, `Cockpit's background service could not start: <reason>`, and opens its window. `window.api.daemon` has `status()` (`running`, or `down` with the reason and whether the log file exists), `retry()` (starts again, answers the new status) and `showLog()` (`shell.openPath` on the log), behind `daemon:status`, `daemon:retry` and `daemon:show-log`, each behind `isFromApp`. The root loader reads the status. `/terminal` and a session page show `daemon-down.tsx` in their main area ("Cockpit's background service could not start", "Terminals and agents run in this service. Your projects and workspaces are untouched.", the reason in monospace, "Try again" and, with a log, "Show log"; the view and the sidebar line go while "Try again" waits, and come back with the new reason or stay gone), and the Sessions section shows the muted line `Cockpit's background service could not start: <reason>`. `pty.spawn` rejects with the reason and `sessions:start` is refused with `Could not start <name>: <reason>` before it creates a folder, spawns or stores anything. Projects and workspaces do not need the daemon and keep working.
  - **Terminal page** (`src/renderer/components/terminal-tabs.tsx`, route `/terminal`): tabs and splits that survive leaving the page (the tab state is module-level, so a visit finds the tabs, splits, selection, output and running shells as they were; a reload, a window close or a quit leaves the shells running in the daemon, and the page shows them again, see Restoring). The tab bar (shadcn `tabs`, "Terminal N" with a sibling "Close Terminal N" button, and a "New terminal" button) sits in the page header, passed as `children` of `PageHeader`. Tab numbers count up for the page's lifetime and are never reused; closing the selected tab selects the one on its left, and with no tab left the page shows "No terminal open" and a "New terminal" button. A tab's terminals form a binary tree of equal halves ("Split right" or "Split down", nestable, no drag resize); each terminal has "Split right", "Split down" and "Close terminal" buttons shown on hover and focus. **Flat layout**: every terminal of every tab is rendered in one list keyed by a terminal id and absolutely positioned from its tab's tree (percent boxes), so a split, a close or a tab switch never remounts a view; the terminals of other tabs are `invisible` and keep their size. A pane's terminal is a live terminal (`live-terminals.ts`, see Sessions), created and spawned (at 80 x 24, resized once `spawn` resolves if its size changed) when the pane first renders; the module-level `dispatch` closes the terminals an action removes ("Close Terminal N", "Close terminal"), which kills their shells, so closing ends a shell and leaving the page does not. The buttons of a pane are rendered only while its tab is shown: a hidden tab's buttons, with their own `transition-all`, would stay hit-testable for a moment after a tab switch. The terminal component (`terminal.tsx`) is only the view: it moves the live terminal's element into its container and out again, skips `fit()` while its area has no size, and takes the keyboard when its `focused` prop turns true (a new terminal, a re-selected tab, the sibling of a closed one: in `A | (B / C)`, closing C focuses B, not A). Colors come from the page tokens (the 16 `--terminal-*` ANSI tokens, light and dark; background, foreground, cursor and selection reuse existing tokens) and are read again when the color scheme changes. Copy and paste use Electron's default macOS Edit menu, which fires the DOM events xterm.js handles.
  - **Early keys**: keys typed before `spawn` resolves are held and written to the shell, in order and in one write, right after the session id is set. They are discarded if the spawn rejects (a `failed` flag stops holding them), the shell has already exited or the terminal is closed first. A rejected spawn writes `[Could not start the shell: …]` in the terminal, unless its pane was closed meanwhile. The tty buffers them until the shell reads, so its own startup loses nothing.
  - **Spawn defaults**: `window.api.pty.spawn` only needs `cols` and `rows`. The main process fills in the rest (`withSpawnDefaults` in `src/main/index.ts`): the `SHELL` of `await shellEnv` (`/bin/zsh` when unset) as a login shell (`-l`), the home directory, and `terminalEnv()` as the environment: `await shellEnv` without the inherited `COCKPIT_SESSION_ID`, `COCKPIT_WORKSPACE_PATH`, `COCKPIT_SOCKET` and `ELECTRON_RUN_AS_NODE` (no pty's environment holds the daemon's runtime switch), with `TERM=xterm-256color`, `COLORTERM=truecolor` and `COCKPIT_SOCKET`, the daemon's `.sock` (see Daemon). Options the renderer passes win. `-l` belongs to the default shell only: a request with its own `command` and no `args` runs it with no argument.
  - **Only `commands` terminals end with their page**: the main process kills a window's `commands` terminals (setup and teardown, see Workspaces) when its main frame commits another document (`did-navigate`, a reload included) or the window is destroyed, or, for a navigation that ends on an error page (a URL such as `/%`, which Electron refuses with `did-fail-load` code -9; a 404 from the `app` protocol does commit a document and is handled through `did-navigate`), `did-fail-load` on the main frame with any code but `ERR_ABORTED` (-3), so a navigation the guard blocks ends nothing. A `shell` or `session` terminal is never killed by a navigation, a reload or a window close; a terminal closed in the page kills its own process ("Close Terminal N", "Close terminal"), and deleting a workspace or removing a project kills the sessions that ran in it (`endSessions`). The daemon also ends every `commands` terminal of a connection that closes (the app quit, or killed with `SIGKILL`) within 5 s. **Late spawn ack**: each page has a count of the times its runs were ended, and `spawnFor` reads it before the spawn (or takes the count its caller read); `sessions:start` reads it at its entry and, once harness detection and the worktree check have returned, refuses without creating a folder or spawning when it changed (a reload during detection starts nothing); a spawn that resolves after its page navigated or was destroyed (the daemon was stopped or busy) kills the terminal at once and throws `PageGoneError`: `sessions:start` lets it reach its existing `catch`, which removes the folder and saves nothing, while the `pty:spawn` handler catches it and returns `-1` (the reply reaches no page), so Electron logs no `Error occurred in handler`, which the tests count as an error, and a reloaded page leaves no orphan shell.
  - **Restoring** (COCKPIT-55): `window.api.pty` has `list()` (the `shell` and `session` terminals every connected daemon runs, in creation order, with `id`, `kind`, `cwd`, `cols`, `rows` and, for a session, `sessionId`, `workspace` and its last reported `status`; `commands` terminals are not listed) and `attach(id)` (makes the calling window the owner and answers `{ cols, rows, screen, seq }`), behind `pty:list` and `pty:attach`. The root loader calls `restoreTerminals()` of `live-terminals.ts` once per page load (and `restoreTabs` of `terminal-tabs.tsx` with its shells): each terminal gets a live terminal (`attachLiveTerminal`) whose xterm.js view takes the pty's size and writes the daemon's serialized screen, scrollback included; a session goes into the store with the status dot it last reported and shows no "Ended"; the shells come back as one tab each, in creation order, with the splits flattened (the layout is not saved). The daemon keeps, per terminal, a headless terminal (`@xterm/headless` `^6.0.0`) resized with the pty and serialized on `attach` (`@xterm/addon-serialize` `^0.14.0`, in memory only, nothing on disk); both it and the view keep `SCROLLBACK` (1000 lines, `@cockpit/daemon/scrollback`) of scrollback. Every chunk of output carries a sequence number, per terminal: `attach` answers the screen up to a number and every later `data` event has a higher one (`pty:data` carries it to the page), so no byte is lost or shown twice; the page drops what the screen already covers. A terminal that ended while no window was attached is not listed, and a session of it shows "This session has ended.".
  - **Single instance** (COCKPIT-54): `app.requestSingleInstanceLock()` at the top of `src/main/index.ts`, right after `app.setPath('userData', …)` (Electron ties the lock to the userData folder, so test launches with their own `COCKPIT_USER_DATA_DIR` stay independent, and the dev build, whose userData is `@cockpit/desktop`, never blocks the installed `Cockpit`). A process that does not get it calls `app.exit(0)` and runs nothing else: no window, no write to `state.json`, the daemon's socket or its token. In the running app a `second-instance` handler, registered next to `activate` in `whenReady`, focuses the first window (`restore()` if minimized, `show()`, `focus()`, and `app.focus({ steal: true })` on macOS) or, with no window, creates one as `activate` does. Arguments and files of the second launch are ignored. An unpackaged build defaults `COCKPIT_HOME` to `~/.cockpit-dev`, so a development build never shares a daemon with the installed app.
  - **Quit**: `app.quit()` (Cmd+Q) and a `SIGKILL` of the app leave the daemon and every shell and session running (checked 5 s later); the next launch finds them again. Only the app's `commands` terminals end, through the closing of its connection. A packaged-app test checks it with a shell and a session.
  - **Transport: HTTP over the daemon's Unix socket, then IPC.** The client sends `GET /attach` with `Upgrade: cockpit-1` and `Authorization: Bearer <token>`; after the `101` the socket carries one JSON object per line in both directions. Requests (`hello`, `spawn`, `list`, `attach` answer; `write`, `resize` and `kill` do not) are `{ id, type, … }` and answers `{ id, result }` or `{ id, error }`; the daemon pushes `{ type: 'data' | 'exit' | 'status', … }`. `hello` answers `{ protocol: 1, build, pid }`; `spawn` takes `{ kind, command, args, cwd, env, cols, rows, sessionId?, workspace? }` (`kind` is `shell`, `session` or `commands`; a `commands` terminal is bound to the connection that spawned it). A request without the right token gets `401` with an empty body before anything else is read. Each output chunk goes daemon, then main (`webContents.send`), then renderer. A `MessagePort` between the daemon and the renderer is not possible (the daemon is not an Electron process of the app), and no measurement shows the main process as a bottleneck for one terminal. **Trigger to move**: a measurement showing typing latency, or a saturated main process, with several terminals active at once (agent sessions).

- **State**: the app state lives in one JSON file, `state.json`, in `app.getPath('userData')` (so `COCKPIT_USER_DATA_DIR` isolates it in tests). `version`, `editor` and `terminal` (the ids of the apps opened last, strings, optional on disk and read as none without rewriting the file; a value that is not a string makes the file corrupted; written only when set, by the pure `rememberApp(state, kind, id)`), `projects` (`{ path }[]`, the repository roots as git reports them, in insertion order) and `sessions` (see Sessions) exist so far; a feature that stores a field adds it, with a write API.
  - `packages/state` holds the logic and does not import `electron`: `loadState(dir)` reads `<dir>/state.json`, creates the folder and writes `{ "version": 1 }` when the file is missing, and `NewerStateError` is what it throws for a newer file. `projects` is optional on disk and reads as `[]` when absent, without rewriting the file (a file from an earlier build stays as it is, version 1). The write API is `saveState(dir, state)` plus the pure `addProject(state, path)` (throws `ProjectExistsError` for a path already listed) and `removeProject(state, path)` (an unknown path changes nothing); they return a new state. The main process keeps the loaded state in memory and replaces it after each successful `saveState`. The main process calls it first thing in `whenReady`, before the daemon and the window, with `userData`.
  - **Atomic, durable write**: every write goes to `state.json.tmp`, is flushed with `fsync`, renamed over `state.json`, then the data folder is opened and `fsync`ed so the rename itself survives a power loss, with synchronous `node:fs` (tiny file). A crash leaves the previous `state.json` intact; a leftover `.tmp` is ignored and overwritten. Node's `fsyncSync` goes through libuv, which on macOS already issues `F_FULLFSYNC` (falling back to `F_BARRIERFSYNC`, then `fsync`), so only the folder sync was missing.
  - **Corrupted file** (not JSON, not an object whose `version` is a positive integer, a `projects` that is not an array of objects with a string `path`, or a `sessions` that is not an array of objects with string `id`, `name`, `harness`, `directory` and `createdAt`, and a `project` that is a string when present): kept as `state.json.corrupt-<timestamp>` with its original bytes (a hard link, so `state.json` is never missing; a copy when the volume cannot link; a name already taken goes to the first free `-2`, `-3`…, and an existing backup is never overwritten), a fresh `state.json` is written, and a warning names the backup.
  - **Newer version** (`version` above the one the app reads): the file is left untouched, no window opens, the message "written by a newer version of Cockpit" goes to stderr (and to an error dialog outside background mode), and the app exits with code 1.
  - **Unreadable file** (a read fails for a reason other than the content: a folder named `state.json` gives `EISDIR`, a file without read permission gives `EACCES`): `loadState` throws the original error and touches nothing. The main process quits as for a newer version (nothing set aside, no window, stderr, error dialog outside background mode, exit code 1) with a message that starts "Cockpit cannot read its data", then names the path of `state.json` and the error message.

The main process keeps at most one `watchWorktree` per `WebContents` (`workspaces:watch` is an invoke handler, `workspaces:unwatch` a message; both behind `isFromApp`), closed on unwatch, on a newer watch, on `did-navigate` (a reload included), on `destroyed` and on a watcher error, and sends `workspaces:changed` to its window. A request counter drops a check that returns after something newer was asked, and the preload's stop sends `workspaces:unwatch` only when no newer `watch` began, so a late stop never ends the watcher of the page that replaced it. The panel watches only while mounted: closing the sidebar, leaving the workspace page or reloading stops it, and no git command runs for the changes view until it opens again (a test with a logging `git` wrapper checks it). Each `changed` event reads the list and the selected diff again (the list is keyed by workspace path, so another workspace's page starts clean). The watcher also sees the git metadata (see `watchWorktree`), so a commit, a push or a fetch made in the session's terminal reaches the ship section's git state within 5 s without a window focus. The main process passes `await shellEnv` to the watch (it runs git to find the folders). No polling.
    - The shared `Api` declares `ChangedFile` and `FileDiff` itself, with the shape `@cockpit/workspaces` gives: importing them would pull the package's Node types into the renderer's typecheck.
  - **Session status** (COCKPIT-36): `sessions:start` runs `statusLaunch` (with `statusCommand`, `$COCKPIT_HOME/plugins` and the session's environment) and puts its `args` before `harness.start(prompt)` and its `env` on the spawn (the harness reports to the daemon, which `statusLaunch` is given through `COCKPIT_SOCKET`). A start refuses a harness whose binary was removed since detection (`Could not start <name>: <path> not found.`) before creating a folder or spawning. The daemon records the last status of each session and sends every report to its clients (`404 { "error": "unknown session" }` to a hook whose id is not a session it runs); `reportSessionStatus` sends `sessions:status` (id, event) to the window that holds the session's terminal on a change (the status is seeded from `pty:list` after a relaunch) and, for `waiting` or `finished` when `BrowserWindow.getFocusedWindow()` is null, shows one `Notification` titled with the session's name and bodied "Needs input" or "Ready"; a repeat of the current status, `working` and any report while a window is focused show none. Clicking it shows and focuses the first window and sends `sessions:open`, and the root layout navigates to the session's page; with no window open it creates one on `/sessions/<id>`. `window.api.sessions` has `onStatus(listener)` and `onOpen(listener)`. The live-terminal store keeps the last status and the exit of each session and publishes `getSessionDots()` (session id to the dot's accessible name, replaced on every change): "Working", "Needs input", "Ready" while it runs, none before its first report; once the process exited "Ended" (exit code 0, a signal, no code, or a session of an earlier launch) or "Exited N", whatever it reported. The row draws it as a `role="img"` dot with `aria-label` and `title` (`--status-working`, `--status-waiting` and `--status-ready` tokens, light and dark; `bg-destructive` for "Exited N", `bg-muted-foreground` for "Ended"). A daemon that cannot start shows the muted line `Cockpit's background service could not start: <reason>` in the Sessions section (see Daemon). Statuses are not persisted to disk (the daemon keeps them in memory). Not done: status for the terminal page's shells, on the session page itself, in the window title or the Dock badge.
  - **Ship section** (COCKPIT-38): a block of the Changes sidebar between its top strip and the file list (`src/renderer/components/ship-section.tsx`, mounted by `changes-panel.tsx`). A "Commit message" field and a "Commit" button (disabled while the message is blank or nothing is uncommitted; the message is trimmed, the field cleared on success and kept on a failure), a "Push" button shown only while the branch has commits its upstream lacks (or, with no upstream, commits beyond the merge-base with the base), and the branch's pull request: `#<number> <title>` as a link (a `target="_blank"` link, so the window open handler sends it to the system browser), its state (`Open`, `Merged`, `Closed`) and, for an open one, `Checks pending`, `Checks passing`, `Checks failing` or `Checks unknown` (nothing without a check). Without an open or merged pull request, a "Create pull request" button, disabled with `Push the branch first.` while the branch has no upstream or unpushed commits; it opens a dialog "Create pull request" (`<branch> into <base>`, the base being the changes base without `origin/`) with a focused "Title" prefilled with the subject of HEAD's commit and an empty "Description". A merged pull request shows "Delete workspace…", which opens the sidebar's own Delete workspace dialog (`requestDeleteWorkspace` in `projects.tsx`: the `deleting` state is module-level, read with `useSyncExternalStore`; the dialog and its `onRemoved` are unchanged), so the removal, the teardown and the ending of the sessions are the existing flow. Nothing about commits, pushes or pull requests goes into `state.json`.
    - **IPC**: `window.api.workspaces` has `status(project, path)` (`{ status: 'read', branch, upstream, uncommitted, unpushed, subject }`), `commit(project, path, message)`, `push(project, path)`, `pullRequest(project, path)` (`{ status: 'read', pullRequest }`, `null` without one) and `createPullRequest(project, path, title, body)`, behind `workspaces:status`, `workspaces:commit`, `workspaces:push`, `workspaces:pull-request` and `workspaces:create-pull-request`, each behind `isFromApp`, `forProject` and `findWorkspace` (so a project not in the state or a path that is not a linked worktree is refused with the messages of `changes`, and nothing runs). Refusals: `Write a commit message.`, `Nothing to commit.`, `Write a title.`, `<name> has no branch.` (`push` and `createPullRequest` on a detached HEAD; `pullRequest` reads `null` there); a failing commit is `Could not commit: <git's message>`, a failing push `Could not push <branch>: <git's message>`, a failing `gh pr create` `Could not create the pull request: <trimmed stderr>`; a `pullRequest` read that `gh` cannot answer is a refusal with `The GitHub CLI (gh) is not installed.` (`GH_MISSING`), `gh is not logged in. Run gh auth login in a terminal.` (`GH_UNAUTHENTICATED`) or `Could not read the pull request: <trimmed stderr>`, shown in the section with no "Create pull request" button (commit and push still work). `subject` comes from `headSubject` in `@cockpit/workspaces`, not from `branchStatus`.
    - **When the pull request is read** (`src/renderer/components/pull-request-reads.ts`, `readPullRequests(project, path, onResult)` returning `{ refresh(), stop() }`): when the section mounts, when the window gains focus, and after a commit, push or pull request creation succeeds; never because a file of the worktree changed. One `gh` read runs at a time, and a request made meanwhile triggers exactly one more read after it. While the last result is an open pull request with pending checks it is read again every 30 s; an unknown, passing or failing summary, a merged or closed pull request, no pull request and a refusal are not polled. `stop()` (the section unmounting: the sidebar closed, Home, another page, a reload) ends the focus listener and the timer, so no `gh` runs while the sidebar is closed. The git `status` is read with the changes list (on open and on each worktree or git metadata event) and after a commit or a push, never the pull request.
    - **Risks**: a pull request an agent opens while the sidebar is open shows only on the next focus or action; `statusCheckRollup` values are GitHub's GraphQL enums, and a new one reads as `Checks unknown` until the list in `packages/github` is updated.
  - **Built assets use absolute paths.** electron-vite forces `base: './'` for a production build, whatever the config says, so a nested route such as `/sessions/<id>` loaded its assets from `/sessions/assets/` (404) on a reload. A small `post` plugin in `electron.vite.config.ts` sets `base: '/'` after it.
- **Runtime tests**: no version ships with a risk of crashing at runtime. `build` and `typecheck` are not enough: `test` (vitest + Playwright, in `test/`) launches the app the four ways it runs, the `dev` script, the built app, the packaged `Cockpit.app` and the packaged app launched with launchd's minimal environment (as from the Finder or the Dock; `open` would pass on the caller's environment), and checks that each one renders, keeps Node out of the renderer, logs no error and keeps running. Every feature's tests are split across the four launches:
  - **Split rule.** A feature's full block (every case: dialogs, refusals, edge cases) runs once, in the built app. Each other launch mode runs one smoke path per feature, a single case that goes through the feature's IPC end to end (the stubbed picker or the page, then the main process, then the disk). The launchd-environment mode keeps only the smoke paths that spawn git or a shell (terminal AC12 is its shell test), since its point is the minimal environment and not the code paths. A mode-specific check runs in every mode it applies to. These are the checks on what differs between the launches: the home page and version, Node out of the renderer, the color scheme, reload, the background switch, the data folder, the output from the first line, `window.api.pty` spawn and echo, `getShellPath`, "logs no error and keeps running", the navigation guard, the node-pty prebuilds. A feature added later gets a full block in the built app and a smoke path in the other modes.
  - **Principle.** Keep the suite as fast as possible without losing coverage. An assertion runs in every launch mode only when what it checks differs between modes, and once otherwise. A behaviour is tested at the lowest level that can observe it: a package's vitest tests before Playwright. No fixed pause where a wait on a condition works.
  - Test launches stay unnoticed. Variables read by the main process before `ready` and honoured in the packaged app too: `COCKPIT_TEST_BACKGROUND=1` (macOS accessory policy, so no Dock icon and never the frontmost app; windows are never shown and keep rendering as if visible), `COCKPIT_USER_DATA_DIR=<dir>` (sets `userData`) and `COCKPIT_HOME=<dir>` (where worktrees, session folders and the daemon's files live, see Workspaces in the sidebar, Sessions and Daemon). A fourth, `COCKPIT_TEST_APPLICATIONS_DIR=<dir>`, replaces the three applications folders for the detection of editors and terminals (ignored when empty) and is set by the launches that open a workspace, with fake bundles in it. The tests set all three on every launch, with a fresh `mkdtemp` folder removed after the app closes (`COCKPIT_HOME` is a folder inside it; only the test of its default leaves it unset or empty, with a `HOME` of its own). The app's own data must therefore live under `app.getPath('userData')`, so the variable isolates it, and its worktrees, session folders and daemon files under `COCKPIT_HOME` (a short folder, `<data folder>/h`, so `daemon-1-<build>.sock` fits in 103 bytes), so no test creates one under the user's `~/.cockpit`. `COCKPIT_TEST_DAEMON_BUILD=<build>` plays an app update. The daemon outlives the app, so a launch's `close()` kills the daemons of its home through their `.pid` files, and a vitest global setup (`test/global-teardown.ts`) kills any daemon whose `.pid` sits under a `cockpit-*` or `ck-*` folder of the temporary directory, when a test failed before `close()`; a pid whose command line lacks `--cockpit-daemon` is left alone.
  - **Stopping a launch.** `stopGroup` sends `SIGTERM` to the launch's whole process group and waits until no process of the group is alive, not only for the spawned child to exit (Electron's helpers can outlive `bun run dev` and still write in the data folder, which made `rmSync` fail with `ENOTEMPTY`). It sends `SIGKILL` to the group after 10 s and throws an error naming the group after 20 s. Every launch's `close()` goes through it.
  - The launch without the switch (visible window, `Foreground` app) runs only in CI, where no one's focus is at stake: `CI` reaches the tests through `turbo.json`. Do not set `CI` locally to run it.
  - **Folder picker stub**: the tests launch the app with the Node inspector (`--inspect=0`; `--inspect <free port>` for the dev script, which ignores 0), read the `Debugger listening on ws://…` line, connect with Node's global `WebSocket` and call `Runtime.evaluate` with `includeCommandLineAPI: true`, which exposes `require`, to replace `require('electron').dialog.showOpenDialog` in the main process. The app has no test hook for it. Keep `--inspect` usable in test builds, like the remote debugging port: it depends on Electron's `EnableNodeCliInspectArguments` fuse (on by default, untouched by `electron-builder.yml`), so a later fuse hardening must keep test builds able to use it. The helper disconnects the inspector before stopping the process group, since a connected inspector can hold the process at exit.
  - Playwright is maintained by Microsoft and widely adopted. The tests do not use its Electron launcher (`_electron.launch()`, labelled experimental): it runs the app's main script before it returns, so output written during startup never reaches the test. They spawn the app themselves with `--remote-debugging-port=0`, attach the output listeners at once, read the port from Chromium's `DevTools listening on ws://127.0.0.1:<port>` line on stderr, and attach with `chromium.connectOverCDP`. The session's `output()` therefore holds everything the app wrote from its first line. Before its first reload, `attach` waits until the page is on the app's URL and loaded: the window's target starts as `about:blank` while its first navigation is pending, and a reload racing it never completes. The attach goes through Chromium's remote debugging port, so never disable it in test builds.

## Workspaces (`packages/workspaces`)

Pure Node, consumed as TS source like `packages/daemon`, with no `electron` import (a test checks it). Fourteen functions: `findRepositoryRoot`, `listBranches`, `listWorktrees`, `createWorktree`, `removeWorktree`, `readWorkspaceConfig`, `listChanges`, `fileDiff`, `branchStatus`, `headSubject`, `commitAll`, `pushBranch` and `watchWorktree` (the last seven of those, from `listChanges` on, in `src/changes.ts`) and `commandsInvocation`. All but `commandsInvocation` take an optional `env` used to run git (`watchWorktree` takes it in an options object as its fourth parameter), so the caller can pass the login-shell environment.

- **A package called by the main process, not a CLI.** Checked on 2026-10-19 against the source of Superset, Orca, Emdash, Vibe Kanban and Claude Squad: none of them has its app call its own CLI. Errors are typed (`WorkspaceError` with a string `code`, which survives IPC). The main process wires them (see Workspaces under the desktop app).
- **`execFile('git', …)` on the user's git, no git library.** Never through a shell. The git manual guarantees that the output of `git worktree list --porcelain` stays stable. Against the libraries: simple-git has no worktree API and one de facto maintainer; dugite ships its own git binary, which would have to be signed; isomorphic-git has no worktrees; nodegit's last stable release is from 2020. Typed errors come from pre-checks and exit codes, never from git's localized messages.
- **git 2.36 or later**, checked at runtime by every public function (`GIT_MISSING`, `GIT_TOO_OLD`): `listWorktrees` parses `git worktree list --porcelain -z`.
- **Layout**: `<root>/<project>-<hash>/<branch>`, where `<project>` is the basename of the main working tree and `<hash>` the first 8 hex characters of the SHA-256 of its path (deterministic, stateless, no collision between two repositories with the same name). A branch with a slash nests (`feature/login`). The root is a parameter: choosing the real one is the app's job.
- **`listBranches(repo, { env })`** gives `{ local, remote, defaultBase }` from `git for-each-ref` (symbolic refs skipped, so no `origin/HEAD`), local branches and `origin/*` only, with no fetch. `defaultBase` is `origin/D` when it exists, else the local `D`, else `null`, where `D` is the branch `refs/remotes/origin/HEAD` points at or, without it, the one checked out in the main working tree.
- **`INVALID_BRANCH_NAME`**: `createWorktree` throws it when `git check-ref-format --branch` refuses the name or rewrites it (`@{-1}`). Calls for one repository run one at a time (a chain of promises per repository root), so of two creating the same branch the second gets `BRANCH_EXISTS` and the winner is intact.
- **Base and changes.** `createWorktree` with a `base` records it in the repository's git config as `branch.<name>.cockpitBase` before `git worktree add`, and unsets it explicitly in its rollback (`git branch -D` only drops the section of a branch that exists). The base of a workspace is that value when it still resolves to a commit, else `listBranches(...).defaultBase` (so a deleted base branch and a worktree made with plain `git worktree add` fall back without an error), else `listChanges` rejects with `NO_BASE`.
  - `listChanges(worktree, { env })` resolves `{ base, files }`, the working tree (commits, uncommitted edits, untracked files not ignored) against `git merge-base <base> HEAD`, as a pull request shows it. `files` are `{ path, status: 'added' | 'modified' | 'deleted' | 'renamed', oldPath?, additions, deletions }` sorted by path, with `null` counts for a binary file. Untracked files are made visible to `git diff` through a temporary copy of the worktree's index (`GIT_INDEX_FILE`, `git add -N -- .`, the copy removed in a `finally`): the real index is never written. Statuses and counts come from `git diff --name-status -z -M` and `--numstat -z -M`.
  - `fileDiff(worktree, file, { env })` resolves `{ kind: 'text', patch }` (git's unified diff of that file, a rename as one patch from `oldPath`, run with `--literal-pathspecs`), `{ kind: 'binary' }` or `{ kind: 'tooLarge' }`. The 1 MiB limit (1,048,576 bytes) is the `maxBuffer` of that git call, set explicitly (`GitOptions.maxBuffer`), so raising the package's default buffer does not change it; `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` is `tooLarge`, never a rejection.
  - `watchWorktree(path, onChange, onError?, { env }?)` resolves `{ close() }` once the folder is watched: recursive `fs.watch` (FSEvents-backed on macOS, so macOS only), `onChange` after 200 ms without an event (trailing debounce, shared by every watched place), nothing after `close()`. It also watches the repository's git metadata, from `git rev-parse --path-format=absolute --git-dir --git-common-dir` run with `env`: the worktree's gitdir (recursive: HEAD, the index, its reflog, so a commit made in a terminal), the common dir's `refs/remotes` (recursive: a push or a fetch) and the common dir itself without recursion, filtered on the name `packed-refs` (git rewrites it by rename, so `git pack-refs` or a gc shows). A folder that does not exist (`refs/remotes` before any remote ref) is not watched, and a `path` outside any repository is watched alone. FSEvents starts each stream after `watch` returns and never reports what happened before, so the start touches the mtime of every watched folder every 10 ms until each has reported an event (2 s at most), then waits 50 ms for the touches' own events to die down; the first events are not reported. `onError` gets a watcher failure (any of the watchers), after which no event comes.
  - **Reading never writes under the gitdir**, or the watcher on it would loop: `branchStatus` runs `git --no-optional-locks status --porcelain`, which does not refresh the index, and `listChanges` and `fileDiff` work on a temporary copy of the index. A test checks that `branchStatus` and `listChanges` on a worktree with a stale index call nothing.
- **Ship (COCKPIT-38).** `branchStatus(worktree, { env })` resolves `{ branch, upstream, uncommitted, unpushed }`: `branch` and `upstream` (`origin/feat`) are `null` on a detached HEAD or without an upstream, `uncommitted` is a non-empty `git status --porcelain`, `unpushed` is a commit count above zero from the upstream to HEAD, or, without an upstream, from the merge-base with the base (`resolveBase`, so `NO_BASE` when there is none). `headSubject` is `git log -1 --format=%s`. `commitAll(worktree, message, { env })` runs `git add -A` then `git commit -m <message>` (a failing hook is `GIT_FAILED` with git's message and no commit). `pushBranch(worktree, { env })` runs `git push --set-upstream origin <branch>` with `GIT_TERMINAL_PROMPT=0` and nothing else: never `--force`, `--force-with-lease` or a `+refspec`; a detached HEAD or a refusal by the remote (non-fast-forward) is `GIT_FAILED`. `removeWorktree` with `deleteBranch` accepts a branch merged into its upstream (`git branch -d`), so a branch pushed with `--set-upstream` whose pull request was squash-merged is deleted.
- **Removal and `force`.** A dirty worktree is refused (`DIRTY_WORKTREE`) unless `force` is set, which skips that check and runs `git worktree remove --force`: it exists for a caller that has asked the user to confirm. A locked worktree is refused either way. A branch is deleted only with `git branch -d`: unmerged, squash-merged included, gives `BRANCH_NOT_MERGED`, with the worktree removed and the branch kept; there is no way to force the branch. `createWorktree` does use `git worktree remove --force` and `git branch -D`, but only to roll back what the call itself created, so a failed creation leaves nothing behind (all-or-nothing).
- **Config file (`readWorkspaceConfig({ repo, path, env? })`).** `<main working tree>/.cockpit/config.json` is `{ "setup": string[], "teardown": string[] }`, both keys optional (absent reads as `[]`), the commands non-blank strings returned unchanged and in order. It is read from the main working tree only, never from the worktree (uncommitted edits included), so a config that only a worktree holds is ignored. A missing file means no commands. A file that cannot be read (`EISDIR`, `EACCES`), is not JSON, or has the wrong shape is `INVALID_CONFIG`, the message naming the file and the reason or the key at fault; any key other than `setup` and `teardown` (Superset's `run` included) is invalid. `path` must be a linked worktree (`GIT_FAILED`, `not a linked worktree: <path>`, checked before the file is read). The result holds `env` with `COCKPIT_ROOT_PATH` (the main working tree), `COCKPIT_WORKSPACE_PATH` (the path git reports) and `COCKPIT_WORKSPACE_NAME` (the branch, or the folder name when detached); merging it into the login-shell environment is the caller's job. Nothing is run by `readWorkspaceConfig`; `commandsInvocation(commands)` gives `{ command: '/bin/sh', args }`, the invocation that runs them (see Setup and teardown scripts in the desktop app).

## Harnesses (`packages/harnesses`)

Pure Node, consumed as TS source like `packages/workspaces`, with no `electron` import (a test checks it) and no runtime dependency. The main process wires it for sessions (see Sessions in the desktop app); worktrees and the other functions are not wired yet.

- **API**:
  - `harnesses`: the catalogue, three `Harness` entries in this order: `claude-code`, `codex`, `opencode`. Each has `id`, `name`, `binary`, `start(prompt?)` (interactive, in the spawn's cwd), `continueLast`, `resume(sessionId)` (argv arrays) and `sessions(env)`, which gives the location and format (`jsonl` or `sqlite`) of the harness's session store, honouring `HOME` and the relocation variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME`; an empty one counts as unset). It reads nothing. The catalogue is deep-frozen (the array, each entry and its `continueLast`; the types are `readonly`), so callers share it and none can change it for the others: a write throws a `TypeError`.
  - `detectHarnesses(env, { timeoutMs })` (default 10 000 ms): serializable `{ id, path, version }` records, in catalogue order, so they can cross IPC.
- **Only verified harnesses are listed.** Verified means official docs, the CLI's own `--help` or output, or the official open source code at a release tag. Each fact carries its source as a comment in `src/catalogue.ts`. Checked on 2026-10-20 against Claude Code 2.1.304, Codex 0.163.0 and OpenCode 2.0.31. These CLIs release weekly and the tests use stubs, so nothing catches a renamed flag: re-check the sources when updating an entry.
  - Codex's session path comes from its source, not its docs.
  - OpenCode's docs still describe the 1.x storage; the 2.x path rests on `opencode debug paths`.
- **Left out (COCKPIT-43)**, for what was missing:
  - **Cursor CLI**: session storage is not documented and the CLI is closed source; the path was only found in the shipped binary. Its binary is now `agent`, with `cursor-agent` kept as a legacy alias.
  - **Kimi**: the legacy `kimi-cli` is archived and its `kimi` no longer runs an agent. Its successor Kimi Code CLI installs the same `kimi` binary but cannot take an initial prompt in interactive mode; detection would also have to tell the two apart.
  - **Mistral Vibe**: left out by decision. 3.0 (Rust rewrite) shipped on 2026-10-19 and its session store layout is only in the source.
- **Detection rules**:
  - The package walks `env.PATH` itself: the first executable regular file named after the binary wins (symlinks followed). Empty and relative entries are skipped, as are directories and non-executable files.
  - It runs `<path> --version` with the given `env`, in its own process group, all harnesses in parallel. Exit 0 means installed, with the first `x.y.z` (optionally with a pre-release suffix) of stdout as `version`, or `null` when there is none.
  - A non-zero exit, a signal, a spawn failure or a timeout means not detected. On timeout the whole group gets `SIGKILL` and detection settles without waiting for `close`, as a background child can hold stdout open. It never rejects.
- **Status reporting (COCKPIT-36)**: `statusLaunch(harnessId, { command, pluginsDir, env })` in `src/status.ts` resolves `{ args, env }` that make a harness report `working`, `waiting` or `finished` through the shell line `command(event)` (`statusCommand` of `@cockpit/control`, passed in: the package does not depend on it). Everything goes through argv and environment, never into the user's repository or global config. Every fact carries its source as a comment in `src/status.ts` (checked on 2026-10-25 against Claude Code 2.1.310, Codex 0.163.0 and OpenCode 2.0.31).
  - **Claude Code**: `--settings <inline JSON>` whose `hooks` run the command: `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `ElicitationResult` report `working`; `PermissionRequest`, `Elicitation` `waiting`; `Stop`, `StopFailure` `finished`; synchronous `command` hooks, `timeout: 5`, no matcher. Cannot report: Esc and a rejected permission fire no hook, so the dot stays as it was; an approved tool keeps "Needs input" until it ends; the workspace-trust dialog of a new folder holds every hook back until the user accepts it.
  - **Codex**: `--no-daemon -c hooks={…}` (TOML inline table): `UserPromptSubmit`, `PostToolUse` `working`; `PermissionRequest` and `PreToolUse` with the matcher `^request_user_input$` `waiting`; `Stop`, `Interrupt` `finished`; `timeout=3`. A hook runs only when trusted, so the same `-c` carries `hooks.state` with, per hook, the key `/<session-flags>/config.toml:<event_snake>:0:0` and `trusted_hash`, `codexTrustHash`: `sha256:` + hex SHA-256 of the key-sorted JSON `{ event_name, hooks: [{ async: false, command, timeout: 3, type: "command" }], matcher? }`. This comes from Codex's source, not its docs: the tests pin the hash of a pair the real Codex 0.163.0 accepted, and a release that changes the formula shows "Hooks need review" with no dot, so re-check it at each catalogue update. Cannot report: a turn that ends on an error fires no `Stop`.
  - **OpenCode**: no hook mechanism on the command line, so a plugin: `statusLaunch` writes `<pluginsDir>/opencode-status/server.js` (temp file and rename, at every OpenCode start), runs with `--standalone` (a private server instead of the shared background service, so the plugin sees the session's environment) and `OPENCODE_CONFIG_CONTENT` whose `plugins` array ends with the folder (the user's object when the login shell already sets one, the legacy `plugin` key untouched; a value that is not a JSON object, or a `plugins` that is not an array, leaves the start as without status and the value unchanged). The plugin reads `ctx.event.subscribe()` and runs the commands one at a time, in order, only when the state changes: `waiting` while a permission or form is pending, else `working` while an execution runs, else `finished` once one has run; an execution that ends drops its session's pending permissions, since OpenCode emits no reply for one interrupted while pending. Cannot report: a plain-text question ends the execution and reports `finished`.
  - Out of scope: overriding the user's `disableAllHooks` (Claude Code), `features.hooks = false` (Codex) or an admin policy (their sessions show no dot), pre-trusting folders, heuristics on terminal output (OSC 9, Codex's OSC 7501, text patterns).
- Out of scope: combining an initial prompt with a resume, prompts that start with `-` (passed as is, not verified), minimum versions, `--version` caching, non-macOS paths.

## Launchers (`packages/launchers`)

Pure Node, consumed as TS source like `packages/harnesses`, with no `electron` import (a test checks it) and no runtime dependency. The main process wires it for the workspace menu (see Open a workspace in the desktop app). It is a package of its own because `apps/` holds no business logic and `packages/workspaces` is about git.

- **API**: `apps`, the deep-frozen catalogue of `{ id, name, kind: 'editor' | 'terminal', bundle }` entries, in this order: `vscode` (Visual Studio Code), `cursor`, `zed`, then `terminal`, `iterm2`, `ghostty`, `warp`. `defaultApplicationDirs(home)` gives `/Applications`, `<home>/Applications` and `/System/Applications/Utilities` (where Terminal lives). `detectApps(dirs)` gives serializable `{ id, path }` records in catalogue order. `reveal(path, { env })` runs `open -R <path>` and `openIn(bundlePath, path, { env })` runs `open -a <bundlePath> <path>`; both reject with a `LaunchError` whose message is the reason shown to the user.
- **Detection by app bundle.** An app is detected when `<bundle name>.app` is a directory (symlinks followed) in one of the folders, the first folder holding it winning. It only stats: no `open`, no Launch Services or Spotlight query, no cache, so it runs at each menu open. Editor CLIs (`code`, `cursor`, `zed`) are not used.
- **Why the bundle's absolute path.** `open -a <name>` goes through Launch Services, which may pick another copy of the app than the one detected (in tests, the runner's real VS Code instead of the stub). Launching `open -a <absolute path>` opens the one detected.
- **Runs.** `execFile('open', …)` with the caller's `env` (the main process passes `await shellEnv`), never through a shell: a path with spaces or `$(…)` is one argument. `open` is found through that `PATH`, like git.
- **Sources** (checked on 2026-10-25; each fact is also a comment in `src/catalogue.ts`). All seven open the folder (editors) or a shell in it (terminals): Visual Studio Code 1.143.1 (`Visual Studio Code.app`, `public.folder`, `microsoft/vscode` `build/lib/electron.ts`), Cursor 3.25.9 (`Cursor.app`, `public.folder` in its `Info.plist`), Zed 1.25.3 (`Zed.app`, `public.folder`, `zed-industries/zed` `crates/zed/resources/info/DocumentTypes.plist`), Terminal 2.15 (`public.directory` in its `Info.plist`), iTerm2 3.7.6 (`iTerm.app`, `application:openFile:` gives a directory to a new session as its initial directory, `gnachman/iTerm2` `sources/AppKit/iTermApplicationDelegate.m`), Ghostty 1.3.1 (`Ghostty.app`, `application(_:openFile:)` sets the new surface's `workingDirectory`, `ghostty-org/ghostty` at `v1.3.1` `macos/Sources/App/macOS/AppDelegate.swift`) and Warp (`Warp.app`; the docs say a folder dropped on its dock icon opens a new tab in it, and a dock drop and `open -a` send the same Open Documents event; the client is closed source, so this rests on the docs, and if a release breaks it the entry must go).
- Out of scope: other editors and terminals (Windsurf, Sublime Text, JetBrains IDEs, kitty, Alacritty, WezTerm…), apps outside the three folders (Setapp), a setting page for the default app, opening a file or a line, running a command in the terminal app, non-macOS platforms.

## GitHub (`packages/github`)

Pure Node, consumed as TS source like `packages/launchers`, with no `electron` import and no runtime dependency. The main process wires it for the ship section of the Changes sidebar (see Ship section in the desktop app). It is a package of its own because `packages/workspaces` is about git.

- **API**: `findPullRequest(cwd, branch, { env })` resolves the newest pull request of `branch` as `{ number, title, url, state: 'open' | 'closed' | 'merged', checks: 'none' | 'pending' | 'passing' | 'failing' | 'unknown' }`, or `null`; `createPullRequest(cwd, { base, head, title, body }, { env })` runs `gh pr create --base <base> --head <head> --title <title> --body <body>` and reads the pull request; `checksSummary(rollup)`; `GitHubError` with a string `code` (`GH_MISSING`, `GH_UNAUTHENTICATED`, `GH_FAILED`) that survives IPC, its message the trimmed stderr or the spawn error.
- **`gh` through `execFile`, never a shell**, found through the `PATH` of the given `env` (the main process passes `await shellEnv`), run in the worktree with `GH_PROMPT_DISABLED=1`. ENOENT is `GH_MISSING`; exit code 4 is `GH_UNAUTHENTICATED` (authentication required, per `gh help exit-codes`); anything else is `GH_FAILED`. The read is `gh pr list --head <branch> --state all --limit 1 --json number,title,url,state,statusCheckRollup`: the newest pull request of the branch, whatever its state.
- **Checks.** `statusCheckRollup` entries are CheckRun (`status`, `conclusion`) or StatusContext (`state`). Known values: CheckRun `status` `COMPLETED`, `IN_PROGRESS`, `QUEUED`, `WAITING`, `PENDING`, `REQUESTED`, with `conclusion` `SUCCESS`, `NEUTRAL`, `SKIPPED` (passing) or `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED`, `STARTUP_FAILURE` (failing) once completed; StatusContext `state` `SUCCESS` (passing), `PENDING`, `EXPECTED` (pending), `FAILURE`, `ERROR` (failing). Any other `__typename`, `status`, `conclusion` or `state` is unknown, never passing. The summary of several checks is the worst of them: failing, then unknown, then pending, then passing; `none` for an empty rollup.
- Out of scope: merging, editing a pull request, drafts, reviewers, labels, `gh auth login`, GitHub Enterprise specifics, repositories with several GitHub remotes and no `gh repo set-default`, other forges.

## Daemon (`packages/daemon`)

Pure Node, consumed as TS source like `packages/harnesses`, with no `electron` import and no import from `apps/` (a test checks it). Runtime dependencies: node-pty (native), `@xterm/headless` and `@xterm/addon-serialize` (bundled into the daemon). It holds the terminals and the status endpoint that earlier builds kept in a utility process and in a control server of the main process. It lets a process the app started (an agent CLI's hook today, the `cockpit` CLI later) reach the daemon and say which session it belongs to; the terminals, the files, the build, the superseded rule and the transport are described under Terminals in the desktop app.

- **API**: `runDaemon({ home, build })` resolves `{ socketPath, close, closed }` once it listens and its files are written, and rejects with an error naming the path at fault; it never calls `process.exit` (the entry does, when `closed` settles). `ensureDaemon({ home, build, spawn })` returns a connected, hello'ed `DaemonClient` (typed `hello`, `spawn`, `list`, `attach`, `write`, `resize`, `kill`, `onData`, `onExit`, `onStatus`, `onClose`, `close`); `connectDaemon(socketPath)` reads the token next to the socket. `daemonFiles(home, protocol, build)`, `listDaemonFiles(home)`, `PROTOCOL_VERSION`, `SCROLLBACK`, `SESSION_EVENTS` (`working`, `waiting`, `finished`) and `statusCommand(event)` complete the exports.
- **Status endpoint**: HTTP over the same socket, JSON bodies. Every request needs `Authorization: Bearer <token>`, compared with `crypto.timingSafeEqual` before the path, the method or the body is looked at; without it the answer is `401` with an empty body. The route is `POST /session-events` with `{ "sessionId", "event" }` and no other field: `204` when accepted, `404 { "error": "unknown session" }` when no terminal of the daemon runs that session, `400 { "error": "<reason>" }` for an invalid body. A body above 64 KiB gets `413` and the connection is closed without reading the rest. Any other method or path gets `404 { "error": "not found" }`. A hook can call it with `curl --unix-socket "$COCKPIT_SOCKET" -H "Authorization: Bearer $(cat "${COCKPIT_SOCKET%.sock}.token")" -d '{"sessionId":"…","event":"working"}' http://localhost/session-events`.
- **Why HTTP over a Unix socket rather than JSON-RPC**: zero dependency either way, and `curl --unix-socket` ships with macOS, so a hook needs no client. Clients find the token next to the socket (`${COCKPIT_SOCKET%.sock}.token`); there is no `COCKPIT_TOKEN_FILE`.
- **Existing path**: a socket that refuses a connect (`ECONNREFUSED`, left by a daemon killed with `SIGKILL`) is unlinked and replaced; an unlink that fails (a read-only home) rejects the start, one that finds the socket already gone goes on. A socket that accepts one belongs to a running daemon of the same build: it and its token are left untouched and the start rejects with `another Cockpit holds <path>`. A path that is not a socket (a file, a folder) is left untouched and the start rejects with `<path> is not a socket`; the token is written only after that check.
- **Environment**: `terminalEnv()` in `src/main/index.ts` builds the environment of a terminal or a session (see Spawn defaults). `sessions:start` adds `COCKPIT_SESSION_ID` (the session's id) and, in a workspace, `COCKPIT_WORKSPACE_PATH` (the worktree path, the session's `directory`; a workspace has no id, git being the source of truth). A `pty:spawn` request that passes its own `env` replaces the whole default environment, so it gets no `COCKPIT_SOCKET`.
- **`statusCommand(event)`**: the one shell line the harness hooks run (by `/bin/sh -c`) to report `event` for the session whose `COCKPIT_SOCKET` and `COCKPIT_SESSION_ID` they inherit: `curl` over the socket with the token read from the `.token` next to it (`${COCKPIT_SOCKET%.sock}.token`). It always exits 0 and prints nothing on stdout or stderr (no socket variable, no listener, an unknown session, a missing token file): a failing hook shows an error in Claude Code and Codex, and the stdout of some hooks reaches the model.
- Out of scope: a login service (launchd, systemd) that starts the daemon, Linux and Windows (the transport, the paths and the spawn sit behind one module, tested on macOS only), an update flow or "restart the background service", saving the `/terminal` layout, setup and teardown surviving the app, moving `state.json` into the daemon, persisting output to disk, notifications while no app runs, several windows sizing one terminal (the last resize wins), a UI to end a session other than its process exiting, a remote or mobile client, harness hooks installed by this package (see Status reporting in Harnesses), the `cockpit` CLI (COCKPIT-37, COCKPIT-56), rotating the token.
